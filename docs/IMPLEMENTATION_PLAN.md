## 1. Порядок работы и техническая основа

Сначала создаются серверный движок, fake/demo-исполнитель, управление и диагностический CLI. LLM, Command, CollectContext, Git и весь пресет проверяются независимо от реального harness. Затем подключаются первый harness и базовый UI: это внутренний MVP. В MVP входят API/UI групп моделей, приоритетный выбор и fallback для первого harness и LLM. Второй harness, переключение между harness и визуальный конструктор добавляются после его приёмки.

Номера этапов — идентификаторы работ, а не строгая последовательность. Рабочий маршрут: **0 (контракты) → 1–2 → 2A → 3–5 → 7 → 8 на fake → 6A → 9 → gate MVP → 9A и 6B → 10–11 → 12**. Проверки интеграций этапа 0 продолжаются независимо; отсутствие второго harness не блокирует этот маршрут. Council входит в полную v1 как необязательный для пользователя способ подготовки плана после внутреннего MVP; ручной ввод плана сохраняется.

Решения, зафиксированные при реализации этапов 0–1:

| Область              | Решение первой версии                                                                                |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| Frontend             | React, TypeScript, Vite; React Flow (`@xyflow/react`) для графа; TanStack Query для серверных данных |
| Backend              | FastAPI, Pydantic, отдельный Python worker с асинхронными адаптерами                                 |
| Хранение             | SQLite/WAL, SQLAlchemy, Alembic; отдельный каталог артефактов                                        |
| Очередь              | Устойчивая очередь и команды управления в БД; один worker-процесс с ограниченной конкурентностью     |
| Обновления UI        | Worker пишет БД; общий API poller 200 мс–2 с на Run; REST и cookie-auth SSE по курсору               |
| Codex                | App Server через stdio, протокол проверяется по установленной версии                                 |
| OpenCode             | Выделенный локальный server для рабочей области, HTTP + SSE                                          |
| Обычная LLM          | HTTP-адаптер OpenAI-compatible Chat Completions                                                      |
| Проверки разработки  | pytest, проверки типов Python, Ruff; TypeScript/ESLint, Vitest, Playwright для ключевых UI-сценариев |
| Сборка и зависимости | uv для Python, npm с lockfile для фронтенда; точные версии выбираются и фиксируются на старте        |
| Процессы Windows     | ProcessSupervisor, Job Objects, экземпляры harness на Run, скрытый фоновый launcher                  |
| Секреты и вход       | DPAPI user-scope, ACL; одноразовый pairing и same-origin cookie/CSRF                                 |
| Git                  | Default run_branch/strict; baseline, allowlist, временный index, intent и сверка hooks               |
| План и схема         | Фиксированные PlanItem, общий PlanControl; semver схемы и required_features                          |

Точные правила находятся в [STATE_MACHINES](architecture/STATE_MACHINES.md), [RUNTIME_CONTRACTS](architecture/RUNTIME_CONTRACTS.md), [EXECUTION_CONTRACTS](architecture/EXECUTION_CONTRACTS.md), [SECURITY_AND_OPERATIONS](architecture/SECURITY_AND_OPERATIONS.md). PostgreSQL, Redis, удалённые workers, worktree и installer не входят в v1.

Новое требование редакции 3: роль или узел выбирает конкретную модель либо группу типа `agent`/`llm`. Например, планирование использует `heavy`, обычное написание кода — `flash`; внутри каждой группы кандидаты вызываются по приоритету. Модель группы всегда привязана к конкретному harness-профилю или LLM-подключению. Семантика определена в [описании проекта, §7.5](PROJECT_DESCRIPTION.md#75-группы-моделей-и-приоритетное-переключение); архитектурные контракты пока содержат прежний запрет автоматической замены и должны быть синхронизированы в этапе 2A. Для прямого выбора этот запрет сохраняется.

Council готовит 2–3 независимых проекта плана, объединяет их и предъявляет пользователю один список вопросов. Только после ответов и явного подтверждения конкретной итоговой ревизии фиксируются PlanItem для нового исполняющего Run. Это подготовка входов, а не редактирование плана активного Run. Исходники для адаптации, ограничения и соответствие нашим этапам описаны в [sources/README.md](../sources/README.md); копии являются справочным материалом, не установленной зависимостью приложения.

## 5. Стратегия проверок

Модульные тесты покрывают самостоятельную логику условий, актуальность контекста, счётчики, разрешение параметров и валидацию графа. Интеграционные тесты используют реальную временную SQLite и Git-репозитории. Сценарии восстановления выполняются с настоящими дочерними процессами и принудительными сбоями в точках до/после внешнего действия.

Для групп проверяются порядок кандидатов, параметры/переопределения, несовместимость, exhausted и отсутствие циклического fallback. Fake harness и управляемый HTTP-сервер воспроизводят подтверждённый отказ, 429/5xx до/после исполнения, неизвестный исход, восстановление между кандидатами и остановку на общем бюджете. Отдельный UI-сценарий создаёт agent/llm heavy/flash, меняет приоритеты, назначает роли и показывает реальное переключение/историю; интеграционная проверка доказывает, что credentials подключений не смешиваются.

Council отдельно проверяет независимость входов, одинаковый manifest, барьер перед объединением, неполный состав, вопросы/ответы и фиксацию PlanItem по ревизии. Скопированные upstream-тесты служат материалом для Python-тестов наших контрактов; их наличие в sources не означает прохождения тестов Agents IDE или работоспособности реальных интеграций.

Контрактные тесты адаптеров воспроизводят обезличенные события подтверждённых версий harness. Отдельные реальные smoke-тесты проверяют подключение, модель, простой шаг, прерывание и продолжение. Их результат фиксируется отдельно: fake-адаптер не доказывает работоспособность внешнего сервиса.

UI-проверки сосредоточены на трёх сквозных сценариях: создать проект/чат и запустить пресет; собрать/сохранить циклический pipeline; закрыть браузер, открыть снова и продолжить остановленный Run. Простое оформление не требует тестов, повторяющих реализацию компонентов.

Ключевой тест независимости: старт через API, отсутствие любых подключённых клиентов во время нескольких переходов, завершение через worker и последующее чтение сохранённого результата. Отсутствие браузера, перезапуск API, смерть worker и reboot — разные тесты.

Windows gate включает реальные Job Objects/потомки, 8.3/junction/subst/длинные пути, Git hooks/signing и DPAPI. Если CI не поддерживает определённый filesystem feature, пропуск фиксируется как unverified и закрывается отдельной проверкой на поддержанной среде. Негативные security-fixtures и сбои до/во время/после внешнего вызова не заменяются моками процесса.

Для нагрузки используется зафиксированный Windows/SSD-профиль: 100 000 событий, большие артефакты и slow SSE. Цели p95: snapshot < 500 мс, первая страница истории < 1 с, доставка сохранённого события при активном клиенте < 1 с; буферы не растут с длительностью запуска. Метрики будущие, их нужно измерить и приложить к приёмке.
