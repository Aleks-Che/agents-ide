# Оптимизация фоновой нагрузки — 20 сентября 2026

Замеры проведены на Windows во время активной работы Agents IDE: 32 логических
процессора, около 59 ГиБ доступной памяти. За отдельный трёхсекундный интервал
worker потреблял 117% одного логического ядра, launcher — 42%, API — 4%.
Это не проценты от суммарной мощности всех процессоров.

## Найденные причины и изменения

- `read_workspace_file` запрашивал `read(cap + 1)`, где общий бюджет manifest
  достигал 64 МиБ. Python выделял большой временный буфер даже для маленького
  файла. Теперь размер чтения равен размеру файла плюс один байт. Сохранены
  проверки лимита, идентичности, ссылок и изменений файла во время чтения.
- `psutil.Process.status()` на Windows проверяет приостановку потоков. Этот
  дорогой вызов использовался только для исключения Unix zombie-процессов.
  На Windows достаточно проверки существования и времени создания процесса;
  Unix-проверка zombie сохранена. Ошибка доступа по-прежнему не разрешает
  передавать чужое задание или считать процесс завершённым.
- Launcher создавал новый HTTP-клиент каждые 250 мс, повторно загружая системные
  сертификаты. Теперь клиент и соединение используются повторно. Файл статуса
  записывается при изменении состояния или PID, а не на каждом опросе.
- Во время внешнего вызова проверка владения и STOP/PAUSE выполняется раз в
  250 мс короткой транзакцией чтения. Heartbeat и осмотр дерева процессов —
  раз в секунду. Завершение вызова и локальный abort проверяются каждые 50 мс.
  Перед фиксацией результатов сохраняются проверки владельца и поколения.

В восьмисекундном профиле worker из 284 собранных стеков 125 заканчивались
на чтении файлов manifest, 100 — на проверке статуса процесса Windows.
В пятисекундном профиле launcher из 63 стеков 48 относились к загрузке
сертификатов нового HTTP-клиента, 14 — к проверке статуса процессов.
Это распределение стеков профилировщика, а не точное распределение CPU-времени.

## Проверка и применение

Прошёл 121 тест: новые проверки выделения памяти, изменений файла во время
чтения, частоты heartbeat, повторного использования клиента; Windows paths;
stage5 review; worker concurrency; recovery/processes; launcher;
execution waits; stage7 review. Проверены шесть параллельных запусков,
STOP/PAUSE, восстановление и завершение дочерних процессов.
`mypy src` проверил 143 файла; Ruff проверяет изменённые файлы.

Интеграционные проверки запускались от обычного пользователя Windows:
песочница не может проверять идентичность некоторых родительских каталогов
профиля. Использовались отдельные временные данные, без перезапуска рабочих
служб. Ограничение числа параллельных задач не добавлялось.

Изменения загружаются при следующем запуске служб. После завершения текущих
задач из корня проекта:

```powershell
./scripts/agents-ide.ps1 stop
./scripts/agents-ide.ps1 start
```

## Второй этап: дисковая активность

Повторная диагностика показала, что предыдущие изменения уже загружены.
Активных запусков не было, но API выполнял около 1130 операций чтения в секунду,
worker — 146, launcher — 64. Размер SQLite — 3 100 442 624 байта.
Свободных страниц в ней только 176 128 байт: VACUUM практически не уменьшит
файл, поэтому уплотнение не выполнялось.

Изменения:

- SQLite использует повторно до пяти свободных соединений и их кеши страниц.
  Дополнительные одновременные соединения разрешены и закрываются после
  использования. Число параллельных задач не ограничено. `engine.dispose()`
  закрывает сохранённые соединения при остановке и обслуживании.
- Поиск границ истории использует отдельные MIN/MAX-подзапросы по индексу.
  Прежний общий агрегат просматривал весь индекс событий запуска на каждом
  опросе. Также опрос событий больше не загружает snapshot/runtime запуска.
- Аренда обычного задания продлевается согласно `heartbeat_seconds`
  (по умолчанию раз в пять секунд вместо раза в секунду). Проверка остановки
  службы остаётся не реже раза в секунду.
- Аренда Council продлевается раз в пять секунд вместо каждых 200 мс.
  Проверка отмены остаётся каждые 200 мс.
- Успешные GET/HEAD-запросы записываются при уровне DEBUG; ошибки и изменяющие
  запросы остаются в обычном логе.

`synchronous=FULL`, WAL и атомарность транзакций сохранены. События не удаляются
и не откладываются в недолговечный буфер.

причин зависаний системы.

## Третий этап: пакетная запись потока ответа

`StreamEventBuffer` объединяет текстовые фрагменты, исходные delta-события
Codex/OpenCode и вывод инструментов с полем `delta`. Совместимые фрагменты
одного сообщения сохраняются одним событием; исходный и нормализованный поток
попадают в общую транзакцию. Поле `coalesced_chunks` показывает число объединённых
фрагментов. Исходные границы сетевых чанков больше не воспроизводятся.

- Размер объединённого события — до 64 КиБ JSON с учётом UTF-8 и экранирования;
  обычные накопленные события ограничены пакетом 256 КиБ. Предел сохранённого
  события — 65 КиБ с запасом под добавляемые поля `source` и `late`. Более крупные
  входные события используют прежний механизм артефактов.
- Остаток сбрасывается каждые две секунды, при завершении блока/ответа,
  исключении, остановке и перед синхронным событием: инструментом, запросом
  пользователю, изменением сессии или состояния взаимодействия.
- Сброс по времени использует существующие циклы наблюдения; дополнительных
  потоков, процессов и соединений для буфера нет.
- Runner и нативные агенты Council сохраняют весь пакет в одной транзакции.
  Проверка владельца/поколения остаётся внутри этой транзакции. Ошибка записи
  не превращается в успешный результат адаптера. Закрытый буфер не принимает
  события от отсоединённого вызова после завершения попытки.
- OpenCode иногда повторяет весь растущий текст. Промежуточные снимки длиннее
  4096 символов архивируются не чаще раза в две секунды для одной части сообщения.
  Нормализованные текстовые delta сохраняются полностью; завершённый снимок
  архивируется сразу. Это предотвращает запись огромного снимка на каждом токене,
  даже когда он уже превышает размер блока.

Интеграционный тест с настоящей SQLite: 1000 текстовых чанков + 1000 исходных
событий + событие инструмента + 100 финальных чанков = **2101 callback → 2 commit**
вместо прежних 2101. История содержит один исходный блок, два текстовых блока и
событие инструмента; их содержимое и порядок относительно завершения попытки
проверены как при успехе, так и при исключении. Это измерение числа транзакций,
а не физических операций SSD и не обещание такого же коэффициента для всей системы.

Компромисс: текст в интерфейсе поступает блоками с обычной задержкой до двух
секунд. При аварийном завершении процесса/потере питания несохранённый хвост
буфера может потеряться. При штатной остановке и завершении он сохраняется.
`synchronous=FULL` остаётся включённым для записанных пакетов.

Проверка: 279 тестов прошли, включая новый буфер, транзакции Runner/Council,
ошибку адаптера, остановку с несохранённым хвостом, длинные Unicode-потоки,
параллельные callback, HTTP/SSE OpenCode, протокол Codex, восстановление и
взаимодействие с пользователем. Ruff, mypy (144 файла) и `git diff --check` прошли.

Изменение применено через `maintenance.offline` без активных заданий.
Новый launch ID — `0056cc38b6764d2f8e310206cef39a23`; launcher/API/worker работают,
`/api/health` вернул 200. Состояния всех существовавших запусков сохранились,
активных заданий Council не было. Реальные модельные вызовы ради измерений
не запускались; устранение зависаний всей системы под нагрузкой не подтверждено.

По запросу размер блока затем увеличен с 8 до 64 КиБ, пакета — с 32 до 256 КиБ,
лимита сохранённого события — с 16 до 65 КиБ (включая служебные поля).
Интервал две секунды и немедленный сброс на границах сохранены. Прошли 24
целевых теста, Ruff, mypy и проверка синхронизации API-контрактов. Три проверки
заполняют блок ровно до 64 КиБ и подтверждают, что текст, нативное событие и
вывод инструмента возвращаются целиком через историю, без подмены артефактом.
Версия с блоками 64 КиБ применена через штатный перезапуск: launch ID
`b6ac744ae5254becb286257f37b2e0f0`, health 200, состояния запусков сохранились.

## Четвёртый этап: история без дублирования инструментов

Аудит рабочей базы показал 1 148 550 `agent.native_event`, 579 056 текстовых
чанков и 45 250 `agent.tool_call`. Тела 23 991 `event_payload` занимали
1 358 508 454 байта, а 236 итоговых `agent_response` — только 751 629 байт.
Крупнейшие группы архивированных тел: `message.updated` — 609 МБ,
`message.part.updated` — 591 МБ, `turn/diff/updated` — 69 МБ,
`thread/resumed` — 47 МБ. Аудит выполнялся с пониженным приоритетом CPU/диска.

В рабочих запросах Runner и Council выключен `record_tool_history`: не
сериализуются и не сохраняются исходные vendor-события, вызовы инструментов,
их потоковый вывод и промежуточные планы/diff. Буфер дополнительно отбрасывает
эти типы, включая события стороннего адаптера. Сохраняются текст ответа,
итоговый результат, ошибки, состояния, сессии, пользовательские вопросы и
разрешения. Протокол инструментов продолжает исполняться внутри агента.

Для передачи прерванной задачи сохраняется не более 20 коротких подсказок
(`tool`, `status`, `summary` до 500 символов), без тел результатов. Они записываются
однократно вместе с ошибкой/передачей задачи и не отображаются как журнал
инструментов. Полная нативная сессия продолжает обслуживать контекст самого агента.

`operations.history.compact_history` удаляет диагностические события и объединяет
старые текстовые чанки до 64 КиБ. Операция требует offline-режима и предварительной
проверенной копии. Текст до/после проверяется SHA-256, управляющие события и
итоговые артефакты сохраняются; закреплённые запуски пропускаются. Payload-тела
очищаются только после проверки прямых и транзитивных ссылок из оставшихся данных.
Одна транзакция обеспечивает откат при ошибке. Уплотнение SQLite возвращает
освободившиеся страницы файловой системе. Событие `run.history_compacted`
обновляет курсор и сбрасывает старую историю в подключённом интерфейсе.

Отдельно `read_history` больше не сканирует весь индекс через общий MIN/MAX:
две крайние позиции читаются индексными поисками, крупный runtime при этом
не загружается. Проверено ограничение стоимости на истории из 20 000 событий.
