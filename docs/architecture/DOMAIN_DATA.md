# Данные и конфигурационные API — этап 2

Проверено 14 сентября 2026 года. Миграции: `0001_foundation` → `0002_domain` → `0003_stage2_review`. Этот документ уточняет реализованные контракты; выполнение графа, полный preflight и восстановление остаются в этапах 3–5.

## Авторизация и транзакции

Все маршруты доменного роутера используют существующую cookie-сессию и CSRF для изменений. Host/Origin не заменяют аутентификацию. Ошибки валидации не возвращают переданное значение секрета; ошибки БД не возвращают SQL/параметры.

Сервисы изменений вызывают `begin_write` до чтения версии объекта, проверки дубликата и выделения sequence. SQLite `BEGIN IMMEDIATE` сериализует такие операции между соединениями; зависимость API завершает commit/rollback до отправки ответа. Вызывающий сервис из worker должен сам завершить транзакцию. Проверки Git/тома выполняются до write-транзакции; identity повторно проверяется перед записью. Внешние вызовы harness/LLM сюда не добавлять.

## Черновики и история

`PipelineTemplate.draft` хранит граф, входы, required_features и настройки. `PUT /api/templates/{id}/draft` требует `expected_version`; неполный черновик допустим в пределах 1 MiB. `POST /api/templates/{id}/publish` требует версию черновика и создаёт неизменяемую PipelineVersion. На этом этапе публикация проверяет структуру nodes/edges и размер, а полный граф/AST/совместимость проверит этап 3. Старый endpoint создания версии сохранён.

Чаты и сообщения поддерживают чтение, изменение с проверкой версии и архивацию. Проект/чат с незавершённым Run нельзя архивировать. Сообщения, шаблоны, подключения и профили сохраняются физически; правка источника не переписывает уже сохранённый input Run. Архивное подключение или профиль не допускаются в новых снимках. Удаления истории через эти API нет.

## Итоговые настройки и Run

Приоритет: глобальные defaults → `PipelineVersion.settings` → явно заданные поля binding → `RunStart.overrides`. Словари объединяются по ключам; списки и скаляры заменяются. По умолчанию `branch_policy=run_branch`, `dirty_policy=strict`, `max_calls=100`. Источник сохраняется для каждой группы и отдельных ключей. Неявное default-значение binding не перекрывает настройку версии. `GET /api/bindings/{id}/resolved` и POST того же маршрута с overrides используют тот же resolver, что и старт.

Для AgentTask профиль роли задаётся ID HarnessProfile в `role_assignments`; выбранная модель роли перекрывает default профиля. Явные параметры `node.config` имеют последний приоритет. LLMRequest ссылается на ProviderConnection через `config.connection_id`. Снимок содержит итоговые настройки узлов, копии используемых профилей/подключений, их версии и непрозрачные ссылки SecretStore. Значений ключей в snapshot/API нет. После ротации прежняя ссылка продолжает указывать на старый ciphertext; GC относится к этапу 12.

`execution_hash` идентифицирует опубликованное определение; `policy_hash` итогового Run дополнительно учитывает разрешённые настройки и выбранные зависимости. Публикация/хеширование окончательной исполняемой схемы и отделение layout уточняются на этапе 3. Исходные сообщения чата, задача и входы копируются в `snapshot.input`; новые/исправленные сообщения не меняют их. Причины ожидания и интервалы активного времени имеют серверные типы; их заполнение выполняющим движком относится к этапам 4–5.

Старт сначала проверяет сохранённый нормализованный запрос по `idempotency_key`/`request_hash`, до чтения изменяемой конфигурации. Повтор возвращает прежний Run, даже если настройки изменились или каталог больше недоступен. Другой запрос с тем же ключом даёт 409. Новый Run, QueueJob и `run.created` фиксируются одной транзакцией.

Команды хешируются целиком, включая `command_type` и `expected_state_version`; сам payload сохраняется для worker. Проверка дубликата предшествует проверке текущей версии Run. Новая команда и увеличение state_version атомарны. Сохранение команды не означает её применение: обработчик появится в этапах 4–5. RunPolicyRevision подготовлена для аудита последующего изменения лимитов; API изменения лимитов появится вместе с resolve.

## Рабочие области

Принимаются абсолютные локальные NTFS-пути на Windows. UNC, WSL и отображённые сетевые диски отклоняются; POSIX-профиль остаётся для тестов. Сохраняются identity каталога и цепочка identity родителей; общий checkout определяется identity Git common directory. Проверка Git не меняет index и не наследует `GIT_*`, подменяющие репозиторий. Ошибки доступа Git не превращаются в ложное «чистый каталог».

Старт ставит Run в очередь без резервации. Сервис `reserve_workspace` предназначен для будущего worker: одинаковый каталог, алиас, вложенные области и общий checkout не могут получить двух владельцев. При занятости он возвращает false и оставляет Run в очереди. Истечение lease или терминальный статус сами по себе не освобождают резервацию: нужен подтверждённый конец дерева процессов из этапа 5. Полная защита открытия файлов от подмены ссылок, subst/8.3 и длинные пути требуют дальнейших проверок V-003. `allow_nonoverlap` не допускается к старту до gate этапа 8.

## Каталоги и генерация

`GET /api/connections/{id}/models` объединяет ручные модели и сохранённый каталог, указывая источник, TTL и unverified/stale/fresh. Изменение URL/credential инвалидирует кэш. Реальный HTTP-probe появится на этапе 7: endpoint test пока возвращает 501 и не записывает фиктивный успех. Секреты в произвольных settings профиля не принимаются; авторизация harness использует его собственный механизм.

Из каталога `backend`:

```powershell
uv run python ../scripts/generate_contracts.py
uv run python ../scripts/generate_contracts.py --check
```

Скрипт без запуска API/БД экспортирует [OpenAPI](../api/openapi.json), [схемы узлов](../api/nodes.json) и [TypeScript](../../frontend/src/api/generated.ts). Режим check сравнивает результат с файлами репозитория и завершается с ошибкой при расхождении; он включён в CI и `scripts/check.ps1`. Упрощённый каталог узлов не заменяет валидацию графа этапа 3.

## Обновление прежних данных

Миграция 0003 сохраняет историю и снимки из 0002. В старых Run отсутствовал исходный запрос, в командах — payload, а в резервациях — полный scope. Эти данные нельзя достоверно восстановить: миграция оставляет nullable-поля, повтор такого старта даёт `idempotency_unverifiable`, а неизвестная резервация блокирует новый захват до явной сверки. Будущий worker не должен исполнять старую команду с `payload_json=NULL` или достраивать snapshot из текущих настроек. Новые записи сохраняют эти данные полностью.
