# Графы и preflight после ревью этапа 3

Статус на 14.09.2026: схема, статическая валидация, AST, импорт/экспорт и конфигурационный preflight реализованы. Worker пока не выполняет графы. Проверка перед внешним действием, capability конкретной модели, изоляция разрешений, baseline/hooks и сверка evidence исполнителем остаются этапам 4–8. Ответ `ok=true` означает отсутствие обнаруженных конфигурационных ошибок; `dispatch_ready=false` явно отражает эту границу.

## Формат и переходы

`GET /api/schema/nodes` выдаёт девять схем узлов, общую закрытую JSON Schema графа, ограничения, варианты выбора модели и перечень AST-операторов. Сервер применяет эти же схемы через jsonschema Draft 2020-12. Неизвестные исполняемые поля, не-объекты в nodes/edges и неоднозначные aliases связей отклоняются. Поддерживается ровно schema_version `1.0.0`; поддержанные required_features выдаёт `/api/capabilities`. Возможности графа добавляются автоматически при публикации и импорте, включая группы из settings.

Граф содержит nodes/edges, необязательные `input_schema`, `roles` (имя → agent/llm) и `visual`. Версия содержит значения входов по умолчанию в `inputs`, настройки и origin. Run накладывает свои inputs поверх значений версии. `input_schema` описывает объект; обязательные значения проверяются preflight/start. В схемах входов и результата поддержан ограниченный набор локальных ключей без `$ref`, удалённых загрузок или рекурсивных схем.

Обычный узел имеет один исходящий переход; End — ни одного; Start не имеет входящих. Condition хранит `expression` на уровне узла и ровно три перехода с `when=true|false|unknown`. `label` — подпись, она не выбирает ветку. Все узлы должны быть достижимы из Start и иметь путь к End.

Обратные переходы маркируются `loop: {id, max_iterations}` с целым лимитом 1–200. После удаления маркированных связей оставшийся граф обязан быть ацикличным: проверка не зависит от порядка nodes/edges. Один loop ID имеет один общий лимит. Worker должен хранить его счётчик и дополнительно ограничивать суммарные посещения и обратные переходы; статический валидатор не заменяет эти счётчики. Глобальные пределы схемы: 200 узлов, 400 связей, 1 MiB JSON, 64 KiB промпта; дополнительно ограничена вложенность JSON и AST.

`edge.assignments` — отображение цели в AST. Разрешены только `work.mode`, `work.feedback`, `work.plan_feedback`; mode задаётся константой initial/repair/next_item. Изменять inputs, модели, разрешения или состояние PlanItem через переход нельзя. `apply_assignments` сначала вычисляет все правые части по прежнему контексту и возвращает обновлённую проекцию work. Её durable-сохранение вместе с переходом — обязанность движка этапа 4.

## AST и контекст

`exists` проверяет наличие: null и false присутствуют, отсутствующее значение даёт false. Неизвестный узел, поле схемы, scope и несовместимые типы дают ошибку конфигурации. Сравнение missing/null даёт unknown; неявных преобразований string/number/boolean нет. all/any/not используют трёхзначную логику. Константы только скалярные; структурированные данные доступны через объявленные ссылки и безопасную JSON-подстановку.

Поддержаны `input.*` (`inputs.*` — совместимый alias), project, run, work, steps и ограниченные artifact-разделы. `steps.<id>.latest` проверяется по полному набору ID независимо от порядка узлов. EvaluationContext содержит текущие cycle_id, scope и evidence_manifest_id; несовпадающий LatestResult возвращает missing. Worker обязан передавать текущую область и цикл, проверять подтверждение результата и выбирать evidence по manifest/версии файлов. Передача произвольного исторического результата без этой проверки запрещена контрактом исполнения.

Подстановка `{{ path }}` однопроходная: значение, содержащее новый шаблон, не вычисляется повторно. В strict-режиме missing вызывает ошибку; в preview-режиме сохраняется исходный placeholder. Python, JavaScript, filesystem и SecretStore из выражений недоступны.

## Конфигурационный preflight

`POST /api/bindings/{id}/preflight` принимает необязательное тело `{inputs, overrides, execution_mode, fake_scenario}`. Режим real выбран по умолчанию; явный simulated описан в [контракте движка](ENGINE_RUNTIME.md). Возвращает:

- ошибки/предупреждения, graph_hash и итоговый execution_hash;
- resolved_settings и источники переопределений;
- кандидатов каждого узла в порядке группы, их параметры, источники и причины disabled/unavailable;
- назначения данных всех кандидатов, включая резервных; секретные значения и ссылки DPAPI не выдаются;
- точные найденные программы Command, cwd, аргументы и политики;
- Git-план с HEAD, веткой, dirty-состоянием и ожидаемым переключением;
- запрошенные формат ответа/бюджет и явные unknown/unverified для неподтверждённых capability, контекстного окна, разрешений и телеметрии.

Preflight не резервирует каталог, не вызывает модель и не запускает программу Command. Проверяются актуальная directory identity, относительные пути и выход через существующий symlink/junction, доступность явно заданных исполняемых файлов, архивность ресурсов и чтение заданной версии секрета через DPAPI. Group с недоступным первым кандидатом разрешается, если остаётся настроенный доступный кандидат; отсутствие всех кандидатов блокирует запуск. Недоступность не является доказательством, что безопасно повторить уже отправленный запрос.

Поддержан общий словарь параметров генерации (reasoning_effort, temperature, top_p, token caps, seed, stop, penalties) с проверкой типов/диапазонов. При фактическом подключении адаптер должен дополнительно сверить точный набор и значения для выбранной модели, формат, контекст и permissions. Неизвестный строгий бюджет, включая стоимость/tokens без подтверждённой телеметрии, блокируется. `max_calls`, `max_node_visits`, `max_backward_transitions`, `max_duration_seconds` ограничиваются сервером. Правило fallback не выводится из HTTP 429/5xx или тайм-аута.

Start повторяет конфигурационные проверки с теми же inputs/overrides и сохраняет engine_version. Git-пробы запуска выполняются перед короткой write-транзакцией, их результат передаётся preflight. Движок этапа 4 проверяет directory identity, scope и доступность ресурсов/секретов под своей резервацией перед dispatch. Реальные capability, permissions, baseline/hooks и актуальность evidence требуют этапов 5–8. Simulated preflight может возвращать dispatch_ready=true только для поддержанных тестовых исполнителей, без реальной сети и записи в проект.

## Хэши, перенос и доверие

`graph_hash` охватывает исполняемые узлы, ссылки, input_schema, роли, loop limits и assignments. Подписи, position и visual исключены. Hash определения PipelineVersion дополнительно включает версию схемы, required_features, inputs по умолчанию и settings. Итоговый execution_hash запуска включает конфигурацию, полный снимок зависимостей и фактические значения inputs. Перестановка элементов массива без изменения смысла не меняет hash графа. Замена кандидата, лимита или входного списка команд меняет доверяемое содержимое.

`POST /api/graphs/import` валидирует весь документ, сохраняет settings/inputs/features и возвращает готовое тело публикации с `origin=imported`. Поля trusted и execution_hash из файла отбрасываются; неизвестные поля не теряются молча. Экспорт выдаёт тот же переносимый формат с заново рассчитанным hash. Ссылки на группы/профили/подключения сохраняются как ссылки, без credentials; группы переносятся отдельно по [MODEL_GROUPS](MODEL_GROUPS.md) с явной привязкой ресурсов. На другой установке ссылки требуется разрешить до публикации/создания привязки.

Миграция `0006_graph_review` сохраняет origin версии. Импортированный черновик не теряет origin при правке, в том числе если клиент опустил поле. UI импорта этапа 10 обязан публиковать серверное тело импорта и сохранять provenance, а не отправлять содержимое файла напрямую как локальную версию. Прямое API создания локальной версии остаётся авторизованным каналом редактирования.

Для запуска импортированной версии клиент передаёт `trusted_execution_hash` из preflight, после показа пользователю конкретных назначений, команд и настроек. Hash из экспортированного файла не является подтверждением. Несовпадающий или отсутствующий hash блокирует Start; подтверждение хранится в неизменяемом запросе и снимке Run. Идемпотентный повтор уже принятого запроса возвращает прежний Run до повторной проверки текущих настроек.

История не переписывается. Старые версии с графами, которые первоначальный этап 3 ошибочно принимал, теперь могут не пройти валидацию. Их следует исправить новым черновиком и опубликовать новой версией; старый snapshot не мигрируется молча.
