# Безопасность и эксплуатация локальной v1

Статус: решения для реализации; это модель ограничений продукта, не утверждение о уже проверенной изоляции. Связи: [runtime](RUNTIME_CONTRACTS.md), [исполнение и Git](EXECUTION_CONTRACTS.md).

## 1. Границы доверия

Приложение рассчитано на одного пользователя и локальные проекты. Репозиторий, вывод команд, ответ модели и импортированный pipeline — недоверенные данные до явной настройки доверия. Контрольные плоскости — серверная конфигурация, схема графа, разрешения и журнал — недоступны агенту для записи. Agent prompt не является механизмом ограничения доступа.

| Источник угрозы | Ограничение и проверка |
| --- | --- |
| Prompt injection в README/diff/отчёте | Содержимое передаётся как evidence, не меняет системный prompt, граф, критерии, разрешения или решение сервера |
| Попытка агента сделать commit/push, прочитать .env | Роли реализации ограничены allowlist; GitCommit выполняет сервер; доступ к секретам и Git control вне разрешений роли |
| Недоверенный импорт | Импорт только черновиком, без credentials и привязок; первый запуск требует доверия конкретному execution_hash; импорт групп требует разрешения ссылок на локальные профили/подключения и не перезаписывает одноимённые группы |
| Недоверенный tool output / HTML | UI экранирует вывод, не исполняет скрипты/HTML и не открывает внешние ссылки автоматически |
| Посторонний сайт → локальный API | Loopback, Host/Origin, cookie-сессия, CSRF и ограничение pairing |
| Подмена пути через symlink/junction | Проверка реального файла/родителя при открытии и workspace identity |
| Утечка через LLM URL или logs | Явный адрес назначения, ограничение протоколов, redaction, запрет ключей в URL/argv |
| Исполняемые скрипты, hooks, плагины harness | Preflight показывает эффективную политику; неподтверждённый sandbox запрещает автономные роли с записью |

Инструкции AGENTS.md и аналогичные правила проекта допускаются только в рамках выбранного доверенного профиля; они не могут расширять разрешения запуска. Внешние правила могут сузить действия и вызвать waiting_input, но ответ агента не может увеличить права. Инструменты реализации не должны иметь права изменять данные самого Agents IDE, SecretStore и commit authority. Если выбранный harness/ОС не позволяет обеспечить требуемую границу, профиль не проходит автономный preflight.

Обычные команды проекта и LLM не получают секреты приложения. Harness может использовать собственную авторизацию, поэтому его effective permissions и наследование окружения проверяются отдельно. «Ограничить cwd» не эквивалентно sandbox; тесты должны проверять фактический запрет доступа.

Система не защищает от администратора ОС или любого произвольного вредоносного процесса с полными правами того же пользователя. Проверка строк на секреты уменьшает случайные утечки, но не гарантирует обнаружение всех секретов; ключевые ограничения — исключение источников и права доступа.

## 2. Импорт и разрешения

Импорт ограничен JSON-схемой, размером и числом узлов. Executable graph, координаты и metadata разделены; удалённые ресурсы, скрипты и зависимости автоматически не скачиваются. Все узлы, включая не соединённые с Start, видны в сводке; недостижимые исполняемые узлы мешают валидации запуска.

Перед первым запуском импортированной версии показываются программы и argv, агентные роли, операции с файлами/Git, LLM назначения, разрешения, число узлов/команд и запросы внешних данных. Подтверждение доверия привязано к execution_hash и policy_hash и хранится отдельно от экспортируемого JSON. Поле trusted из импорта игнорируется. До подтверждения разрешён просмотр и редактирование, но не исполнения. Сводка импорта также показывает все ModelGroup-кандидаты, их профили/подключения и назначения данных.

Изменение команд, промптов, разрешений или источников данных создаёт новую исполняемую версию и требует пересмотра доверия; изменение раскладки — нет. Уже подтверждённая конфигурация не спрашивает разрешение на каждом шаге. Системный пресет поставляется с известным hash, но пользователь всё равно выбирает реальные роли, пути и разрешённые команды в binding. Выбор direct/group переопределяется целиком: прямой выбор модели и групповая выборка не объединяются в одном правиле.

## 3. Локальная авторизация и SSE

Выбор v1 — same-origin cookie для REST и EventSource. Собранный frontend отдаётся FastAPI. В разработке Vite проксирует `/api` и SSE к API; разрешённый dev Origin задаётся явно, wildcard CORS отсутствует. EventSource использует эту сессию, дополнительных токенов в query string нет. Такой выбор соответствует cookie/credentials-модели EventSource. [MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource/EventSource).

Первый запуск API создаёт криптографически случайный одноразовый pairing code на 5 минут: хэш хранится сервером, локальная копия доступна только текущему пользователю в ACL-защищённом runtime-файле. CLI `agents-ide auth pair-code` показывает код в вызывающем терминале; общий серверный журнал его не содержит. Пользователь вводит код в локальной форме, `POST /api/auth/pair` передаёт его в теле. Максимум 5 неуспешных попыток на код и ограничение частоты; после успеха или истечения код уничтожается. Команда локального управления может выпустить новый код, не открывая API без авторизации.

Ответ pairing устанавливает host-only HttpOnly cookie, SameSite=Strict, Path=/api; lifetime 12 часов. Secure включается при HTTPS; plain HTTP на loopback не выдаётся за TLS. Cookie сессии содержит случайный непрозрачный ID, сервер хранит хэш/срок/отзыв. Мутации требуют CSRF-токен из авторизованного session endpoint и точный допустимый Origin; токены и cookie не логируются. CLI после локального pairing работает через тот же API и хранит session только в памяти/защищённом временном cookie jar.

API слушает 127.0.0.1; Host сверяется с точным локальным адресом/портом и явно разрешёнными именами. IPv6 loopback добавляется только при явной настройке. В v1 привязка к 0.0.0.0 или LAN запрещена, сетевой доступ — отдельный будущий режим с TLS и аутентификацией. У фиксированного API-порта default=8765 при конфликте показывается ошибка и предлагается настроить другой, чужой сервис не завершается.

Истечение сессии закрывает/перепроверяет SSE и требует повторного входа, но не влияет на Run. Проверка Origin/Host выполняется также для pairing и SSE. Неавторизованным запросам не выдаются пути, проекты, события или диагностические данные.

## 4. Секреты и адреса провайдеров

Windows v1 использует DPAPI user-scope: зашифрованные записи находятся в каталоге данных с ACL текущего пользователя; БД содержит SecretReference и версию. Отдельного plaintext master key нет; доступ зависит от профиля Windows, поэтому launcher, worker и API работают от одного пользователя, не LocalSystem. DPAPI обычно привязывает расшифровку к пользователю и машине; переносимость резервной копии не предполагается. [Microsoft CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

Секрет задаётся/заменяется через API, но не читается обратно. При ротации создаётся новая запись и атомарно меняется ссылка подключения; старые ссылки сохраняются для незавершённых Run. После восстановления данных без DPAPI-контекста подключения получают secret_unavailable, ciphertext не стирается. Пользователь повторно вводит ключ и явно восстанавливает соответствующую ссылку; обычный backup не экспортирует plaintext и не обещает перенос ключей на другую машину.

Логи, события, argv и URL не содержат секретов; Authorization и cookie всегда редактируются до записи. Сканы контекста исключают известные sensitive paths (.env, key files, credential stores) и обнаруженные значения SecretStore; скан не считается полной защитой. Подозрительный артефакт не публикуется в обычный UI/экспорт, сохраняется пометка redacted/quarantined; секрет не вставляется в сообщение ошибки.

ProviderConnection принимает только http/https, без userinfo и API-ключа в query/path. Loopback HTTP поддерживается для локальных моделей; удалённые назначения требуют HTTPS в v1. Перед сохранением показывается hostname, куда будут передаваться данные. HTTP redirect на другой origin не пересылает credentials и по умолчанию отклоняется. URL из промпта/импорта не меняет подключение; адрес выбирает пользователь в настройках. Timeout и max_response_bytes обязательны, общий размер ответа по умолчанию 10 MiB.

Выборы групп моделей включают в execution_hash/policy_hash стабильные ID, ревизии, имя, тип, упорядоченный список кандидатов с их параметрами, а также непрозрачные ссылки SecretStore и публичные настройки профилей/подключений. Сами секреты, записи `.env` и содержимое каталогов в хеш не попадают. Редактирование или архивация группы после старта Run не влияют на активный запуск: snapshot Run уже хранит полный список кандидатов, и worker использует именно его.

Снимок включает все подключения, в том числе резервные и отключённые, с зафиксированными endpoint/protocol и версиями секретов. Для harness копируются kind, путь программы и несекретные settings, включая явно настроенные назначения данных; отсутствующее подтверждение назначения/возможностей не превращается в verified. Кандидат не расширяет разрешения роли. Изменение endpoint, ключевой ссылки, параметров либо порядка кандидатов меняет execution_hash нового Run и требует повторной оценки доверия. Хеш определения PipelineVersion хранится отдельно как pipeline_execution_hash.

Экспорт группы переносит только её определение и внешние resource_ref, без конфигурации подключения, ключей и ссылок SecretStore. Импорт требует явного отображения каждой ссылки на локальный профиль/подключение, создаёт новые ID и отклоняет конфликт имени; одноимённая локальная группа не перезаписывается. Сам импорт группы не выдаёт разрешений и не подтверждает доверие pipeline; полный импорт графа/доверие при preflight реализуются на этапе 3.

## 5. Windows-пути и идентичность рабочей области

Поддержанный профиль v1 — локальные NTFS-каталоги. UNC, сетевые/отображённые сетевые диски и WSL-пути отклоняются с объяснением; их поддержка не имитируется приведением строки к lowercase.

Сохраняются entered_path, normalized_path и workspace_identity. Для существующего каталога identity строится из идентификатора тома и directory file ID через открытый handle; окончательный путь разрешается через ОС. Регистр, slash, `.`/`..`, 8.3, subst и локальные junction/symlink должны приводить к одному ресурсу, когда это подтверждается ОС. Если identity установить нельзя, автономный запуск запрещён, а не создаётся новая фиктивная область.

Дубликат identity не создаёт новый Project. Резервация использует identity и учитывает также вложенные/пересекающиеся рабочие каталоги и общий Git checkout; регистрация родителя и подпапки не должна давать одновременную запись в одни файлы. Git worktree других запусков пока не поддерживаются как средство конкурентного выполнения.

При чтении файла проверяется окончательный handle; при создании — реальный существующий родитель и тип reparse point, после открытия выполняется повторная проверка. Строковый startsWith недостаточен. Корень записи определяется snapshot; замена ссылки между проверкой и открытием не должна давать выход за него. Небезопасные reparse points отклоняются.

Пути с пробелами/кириллицей тестируются обязательно. Длинные пути разрешаются только при подтверждённой поддержке всей цепочки ОС/Python/harness/Git; preflight сообщает неподдержанное сочетание. Тест 8.3/symlink может требовать возможностей тестового тома; такой тест не считается пройденным только из-за пропуска. Дополнительный ручной capability gate фиксирует результат на поддержанной среде.

## 6. Хранение, очистка и резервные копии

Default data directory: `%LOCALAPPDATA%/AgentsIDE`, подкаталоги db, artifacts, logs, secrets, runtime, temp; путь можно изменить. Данные на сетевой файловой системе v1 не поддерживаются. Артефакты immutable, удаление выполняется по manifest/references.

| Ограничение по умолчанию | Поведение |
| --- | --- |
| 16 KiB event payload | Большие данные — в артефакт |
| 10 MiB stdout/stderr одной команды | Дренировать дальше без накопления, отметить truncated |
| 1 GiB артефактов на Run, 10 GiB общий data budget | Запрет новых действий и управляемая остановка/ожидание limit_exceeded до исчерпания диска |
| 100 000 подробных событий на Run | Сначала группировка delta в артефакты; при достижении порога остановка с отчётом, критичные итоги/команды не отбрасываются |
| 30 дней подробной истории терминальных Run | Фоновой GC удаляет подробные delta и неиспользуемые большие артефакты; summary, команды, переходы, manifests, Git intents и evidence итогов сохраняются |
| Нетерминальные или pinned Run | Автоматическая очистка их данных запрещена |

Около квоты сохраняется запас для остановки и критичных записей. Если доказательства активного Run нельзя сохранить, работа не продолжается. Пользователь видит размер данных и может увеличить лимит или явно удалить историю терминального Run; история выполнения кода в Git при этом не переписывается.

GC использует две фазы: tombstone в транзакции → удаление файлов с проверкой ссылок → финальная отметка; он не удаляет артефакт, на который ссылается другой Run/PlanItem. Минимальный retained cursor обновляется с очисткой. VACUUM/компактация выполняется отдельно при остановленных workers/отсутствии активных записей, не в середине шага. Диагностический экспорт по умолчанию содержит метаданные и редактированные журналы; исходники и полные промпты включаются только по явному выбору пользователя.

Backup — отдельная операция: приостановить новые dispatch/GC, дождаться безопасной границы, остановить writer-процессы, создать согласованный SQLite snapshot через backup API и скопировать артефакты по manifest, сохранить контрольные суммы/версии, затем восстановить работу. Копирование одного live `.db` при WAL не используется как backup. [SQLite Backup API](https://sqlite.org/backup.html).

Backup включает БД, необходимые артефакты, metadata конфигурации и опционально ciphertext SecretStore с пометкой привязки к Windows. Он не является backup рабочих репозиториев. Восстановление сначала проверяет manifest/hash, версии и пути, аннулирует старые sessions локального API и leases, переводит нетерминальные Run в recovering. Resume не выполняется автоматически до сверки реального checkout и неизвестных внешних действий.

## 7. Дистрибуция, обновление и диагностика

Первая поставка — версионированный архив/репозиторий со скриптами PowerShell, Python-пакетом/uv lock и уже собранным frontend. README задаёт поддержанные Python/uv и способы установки Codex/OpenCode; Node нужен для разработки/пересборки, не для отдачи готового UI. Универсальный installer, tray и системная служба не требуются в v1.

Команды `agents-ide start/status/stop`, `auth pair-code`, `diagnostics`, `backup/restore` управляют локальным launcher и отдельными процессами API/worker. Фоновые процессы запускаются скрыто; закрытие терминала launcher не убивает сервисы. Явный stop сервиса сначала блокирует dispatch и останавливает/сверяет активные операции. Регистрация автозапуска в Windows Task Scheduler выполняется отдельной командой по явному выбору пользователя, под его учётной записью; само использование приложения не создаёт автозапуск.

При входе в Windows optional autostart восстанавливает API/worker. После reboot runs проходят recovering. Работа после выхода пользователя из Windows в первом выпуске не обещается. Launcher имеет блокировку одного экземпляра, контролирует процессы с ограниченным restart backoff и показывает ошибку вместо бесконечного crash loop.

Обновление: preflight совместимости → backup → запрет новых запусков и остановка на безопасной границе → миграции → новый runtime → диагностика → разрешение возобновления. Пользовательские шаблоны не перезаписываются. Откат приложения требует совместимой БД либо восстановления backup; произвольные обратные миграции не обещаются.

Диагностика разделяет worker heartbeat, lease, attempt heartbeat, last_external_event, process health, порт, диск/БД, SecretStore, модель/авторизацию и рабочую область. Корреляционные поля: request_id, run_id, execution_id, attempt_id, session_id, generation, command_id. Проверки ОС/путей/Git/process supervisor обязательны в Windows CI; Linux CI полезен, но не заменяет его.

## 8. Проверки угроз и эксплуатации

Fixtures: вредоносные инструкции в README/PAYLOAD.md с попытками прочитать/закоммитить .env, изменить граф и скрыть tool output; импорт с shell/скрытым узлом; подмена junction между проверкой и открытием; неверный Host/Origin/CSRF; просроченный pairing и cookie; redirect провайдера; отсутствие DPAPI-доступа после restore; crash GC/backup; занятый порт; потомок, переживающий родителя; закрытие консоли; длинный Run с 100 000 событий.

## Council: фактическая граница доступа (ревью 16.09.2026)

В текущем LLM-only Council в модель передаётся явно предоставленный текст задачи/контекста и, только merger, принятые черновики. Доступа к файлам/инструментам и read reservation пока нет; agent/harness-запрос отклоняется до постановки задания. Применяется общий HttpLLMAdapter с проверкой URL и SecretStore; закреплённый секрет читается только в worker, ответы санитизируются перед записью. API защищён pairing/CSRF. Подтверждённая ревизия защищена hash и DB-триггерами; UI не может передать чужой или изменённый план в Run. После отмены/потери владения новые обращения запрещены; прекращение локального HTTP не является подтверждением остановки удалённой модели. Миграция старых неподтверждённых намерений не запускает платный replay. Полный контракт и открытые части: [PLANNING_COUNCIL](PLANNING_COUNCIL.md).
