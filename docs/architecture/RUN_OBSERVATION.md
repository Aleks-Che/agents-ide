# Наблюдение и управление Run

Этап 11 расширяет экран **Запуски → Открыть** графом выполнения, лентой событий
и сохранённой историей. Закрытие окна или всех вкладок не отправляет команд Run.
Исполнение, переходы и обработка команд остаются ответственностью worker/API.

## Снимок позиции

`GET /api/runs/{id}/snapshot` читает Run, курсор, selection и observation в одной
SQLite-транзакции. `observation` содержит проекцию закреплённого графа без
промптов и настроек подключений: узлы/связи, последнее посещение каждого узла,
цикл, число попыток, время, решение проверки, ID результата и модель/ресурс
последней попытки. Сведения берутся из StepExecution/StepAttempt, а не из
ограниченного окна событий браузера. Конструктор и живые каталоги не меняют этот граф.

Runner сохраняет `runtime.last_transition` в транзакции перехода и решение
Condition в StepExecution. Для старых Run связь восстанавливается из последнего
сохранённого `transition.selected`; если такого события уже нет, UI показывает
неизвестное значение. Позиция и выбранная связь не вычисляются из AST на клиенте.
Нажатие узла только выбирает подробности и фильтр истории.

## Поток и история

Первое подключение получает snapshot, затем страницу последних событий до его
курсора включительно, затем SSE после курсора. События между этими запросами
доставляет SSE. Повторная доставка дедуплицируется по sequence. Начальная
загрузка автоматически повторяется после временной недоступности API.

При разрыве reconnect использует последний принятый sequence и backoff
0,5–10 секунд. Проверка сессии различает 401 и временную ошибку сети. Browser
offline закрывает источник и переводит только индикатор связи в reconnect.
`stream.closed` и `auth.expired` останавливают подписку. Состояние Run
обновляется из REST; потеря соединения не превращает его в stopped/failed.

`stream.reset_required` (retention, недоступный курсор, slow_consumer) получает
новый snapshot и ограниченный хвост истории, затем подключается после нового
курсора. Он не перечитывает всю историю с начала. UI сообщает о недоступных
удалённых событиях. Последние selection/observation восстанавливаются отдельно.

`GET /api/runs/{id}/history` возвращает события от новых к старым, `next_before`,
`has_more`, `last_sequence` и `min_retained_sequence`. `before` исключающий;
параллельные новые записи не смещают старые страницы. Фильтры `category`,
`node_id`, `execution_id` применяются до пагинации на сервере. Категории:
шаги/попытки, сообщения, инструменты/разрешения, модели/переключения,
команды/Git, проверки/артефакты. Фильтр модели включает события выбора,
пропуска, переключения, исчерпания, начала/завершения и повторов попыток.

Одна страница — до 200 событий и примерно 512 КиБ. Живое окно — до 400
событий и 512 КиБ по консервативной оценке строк UTF-16. В DOM одновременно
не более 12 строк фиксированной высоты; подробности выбранного события
открываются отдельно. История хранит одну страницу данных, прежние страницы
удаляются из Query cache. Серверный буфер каждого SSE-подписчика ограничен
1 МиБ; медленный подписчик получает reset и не задерживает остальных.

## Результаты и управление

Сообщения, доступные tool calls и содержимое событий отображаются как текст.
Ссылки на артефакты принимают только внутренний ID. Неизвестные/удалённые
артефакты дают видимую ошибку. Артефакты и журнал управляющих команд читаются
страницами по 50 записей (API default 100, max 200, `offset`/`limit`).
Список артефактов не загружает body из БД.

`GET /api/runs/{id}/artifacts/{artifact_id}/content` выдаёт до 16 000 символов
с метаданными, смещением и полной длиной. Режим text раскрывает строки отчёта,
diff и stdout с переносами; JSON показывает структуру. Сохраняются отметки
redaction/truncation. API проверяет принадлежность артефакта Run. Большое тело
не попадает целиком в DOM/кеш браузера; подготовка фрагмента на сервере всё ещё
читает один сохранённый body, ограниченный контрактом артефактов.

Кнопки pause/stop/resume/cancel/resolve используют прежний контракт команд:
`command_id`, `expected_state_version`, CSRF, журнал и серверную проверку.
Ответ accepted не выдаётся за завершённую паузу/остановку. После неизвестного
ответа повторяется тот же запрос с тем же ID. waiting_input показывает причину,
подробности недостающих данных/разрешения и форму решения; решение сохраняется
отдельно от команды «Продолжить». Разные вкладки наблюдают одно состояние,
подписка не отправляет управляющих действий.

## Границы проверки

Проверки используют локальную SQLite, реальный API/SSE, Chromium и отдельный
процесс simulated Runner. Покрыты закрытие всех вкладок на несколько шагов,
повторное открытие, две вкладки, pause/resume, reconnect, retention, медленный
подписчик, пагинация, фильтры и большой diff. Пятиминутный обрыв проверяется
виртуальным временем transport-теста. Нагрузочные p95 на 100 000 событий,
production retention/GC и gates реальных harness относятся к отдельным
незавершённым пунктам плана; этап 11 их не закрывает.
