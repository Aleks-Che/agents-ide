# Очередь, события, процессы и бюджеты

Проверенная часть OpenCode 6A и её ограничения: [OPENCODE_RUNTIME](OPENCODE_RUNTIME.md).

Статус: решения v1 для реализации. Связи: [состояния](STATE_MACHINES.md), [исполнение](EXECUTION_CONTRACTS.md), [безопасность и эксплуатация](SECURITY_AND_OPERATIONS.md).

Реализованные этапы и границы описаны в [ENGINE_RUNTIME](ENGINE_RUNTIME.md). Fake запускается явно; очередь, checkpoint, retry/fallback, поток delta и SSE проверены. [Этап 5](CONTROL_AND_RECOVERY.md) реализует resume/reconciliation и Windows ProcessSupervisor; Git/evidence добавлены этапами 7–8. OpenCode подключён с запретом инструментов; разрешённая изолированная запись, interactive permissions и Codex остаются gates 6A/6B. Актуальные имена событий выдаёт единый [каталог](../api/events.json); таблицы ниже задают целевую v1, включая ещё не завершённые возможности.

Выбор кандидата в группах моделей (§7.5) делается только по snapshot Run. Direct-выбор сохраняет прежнюю семантику без автоматической замены. Переключение между кандидатами расходует общие лимиты Run и записывается отдельной StepAttempt с фиксированной причиной. Исчерпание всех включённых подходящих кандидатов переводит Run в `waiting_input` с `model_group_exhausted`; возобновление требует явной команды и сохраняет прежние счётчики.

Сводка выбора `/api/runs/{id}/snapshot.selection` читает закреплённые зависимости,
последнюю StepExecution каждого модельного узла и её StepAttempt. `actual` означает
исполнителя зарегистрированной попытки со статусом/исходом; сам факт `running`
не доказывает получения запроса провайдером. Worker сохраняет в `runtime.node_selections`
по одному checkpoint последнего посещения каждого узла: execution_id, курсор кандидатов,
повторы, раунд и причины пропусков/переключений. Новый узел/визит сбрасывает локальный
раунд, явный resume после исчерпания увеличивает его в том же посещении, сохраняя
историю и общие расходы. Это диагностическая часть runtime, она не меняет immutable
snapshot или execution_hash. Сводка переживает переход к End и retention событий;
полная история более ранних посещений остаётся в попытках/артефактах/событиях.
Для старых Run без checkpoint `history_complete=false`: известные попытки показываются,
утраченные причины пропусков не выдумываются. Причины никогда не переносятся между узлами.

## 1. SQLite и очередь

БД — единственный источник истины; прямой канал worker → API в v1 не используется. Локальная SQLite работает с WAL, foreign_keys и `busy_timeout=5000` мс. Для захвата задания применяется короткая `BEGIN IMMEDIATE` с условным обновлением доступного QueueJob, lease, поколения и версии Run. SQLite допускает только одного одновременного писателя; выбранная модель учитывает эту границу. [Транзакции SQLite](https://sqlite.org/lang_transaction.html), [busy_timeout](https://sqlite.org/pragma.html#pragma_busy_timeout).

Транзакция никогда не удерживается во время вызова агента, HTTP, Git, ожидания процесса или чтения большого файла. Порядок: взять работу → сохранить prepared-попытку → зафиксировать dispatch intent с operation_id и running → выполнить внешний вызов → новой транзакцией сохранить итог, контекст, cursor и RunEvent. До сохранения dispatch intent отправка запрещена; внешние session/turn IDs дописываются после их получения. Prepared без intent означает, что вызов не разрешался, running не доказывает, что он состоялся. Если процесс погиб между вызовом и записью, решение принимает recovery, не очередь повторов.

QueueJob содержит run_id, available_at, claimed_by, lease_expires_at, generation. Рабочий старт и принятые команды устойчивы к повторной доставке. В v1 один штатный worker; тест второго worker обязателен. Максимум одновременно работающих Run по умолчанию — 2, не более одного на рабочую область.

Опрос очереди worker: 250 мс при работе, до 1 секунды при простое. Lease — 30 секунд, heartbeat — раз в 5 секунд. Потерявший возможность продлить lease worker запрещает новые действия и инициирует остановку своих процессов. Поколение защищает записи результата, но само по себе не останавливает внешнего агента.

Поэтому резервация каталога и локальный системный lock держатся до подтверждённого завершения дерева процессов. Новый владелец после истечения lease выполняет recovering и не запускает агент, пока предыдущий владелец/потомки не исключены. Поиск свободной работы пропускает зарезервированные каталоги, чтобы один paused Run не блокировал очередь других проектов.

При SQLITE_BUSY выполняется ограниченный повтор только транзакции БД, не внешнего действия. При недоступной БД/disk full worker прекращает новые действия, останавливает управляемые процессы и сохраняет минимальный recovery-маркер в защищённом локальном журнале, если запись ещё возможна. После восстановления маркер сверяется с БД; отсутствие маркера не считается доказательством отсутствия эффекта.

## 2. Доставка событий API и SSE

Worker пишет события вместе с состоянием. API читает их запросом `run_id = :id AND sequence > :cursor ORDER BY sequence LIMIT 500`; уникальность `(run_id, sequence)` обеспечивается БД. Снимок состояния и `last_sequence` читаются согласованно одной короткой read-транзакцией.

В одном процессе API существует общий poller на Run с подписчиками, а не отдельный poller на вкладку. Интервал 200 мс, при отсутствии новых событий backoff до 2 секунд; без подписчиков poller выключен. Внутренний fan-out только доставляет уже сохранённые события. После рестарта API всё восстанавливается из БД. Redis, файловые сигналы и обещание push-уведомлений от SQLite не нужны.

SSE подключается с same-origin cookie по [контракту авторизации](SECURITY_AND_OPERATIONS.md). Последовательность клиента: REST-снимок → EventSource с `after=<last_sequence>` → обновления. При реконнекте используется Last-Event-ID; если оба курсора переданы, Last-Event-ID имеет приоритет. Курсор не секрет. SSE отправляет heartbeat-комментарий раз в 15 секунд; отключение клиента не влияет на worker.

После retention API знает `min_retained_sequence`. Для слишком старого курсора отправляется `stream.reset_required` с причиной и адресом снимка; соединение закрывается, клиент получает новый снимок и подключается заново. UI отмечает, что ранняя подробная история удалена, а не обещает восстановить удалённые события. Дубликаты удаляются по sequence.

Буфер медленного клиента ограничен 1 MiB; при переполнении он отключается и перечитывает события из БД. Текстовые delta можно группировать не дольше 100 мс; переходы, итоги, команды и намерения коммита фиксируются без такого ожидания. Потеря ещё не сохранённых delta при аварии отмечается `stream.gap`, если harness не позволяет прочитать историю.

## 3. Каталог событий

Общий envelope: `event_version`, `run_id`, `sequence`, `occurred_at`, `persisted_at`, `type`, необязательные `node_id`, `step_execution_id`, `step_attempt_id`, `agent_session_id`, `command_id`, `worker_generation`, `payload`. Не относящиеся к событию поля отсутствуют, а не заполняются фиктивными значениями. Payload — максимум 16 KiB после JSON-кодирования; большие значения заменяются artifact_id.

| Типы | Обязательное содержимое payload |
| --- | --- |
| run.created | pipeline_version_id, snapshot_hash |
| run.state_changed, run.waiting_input | from/to, state_version; для ожидания reason и allowed_actions |
| control.accepted/applied/rejected | command_id, command_type, result либо error_code |
| step.started, step.completed, step.failed | execution_id, visit_index, outcome/result_ref при завершении |
| step.attempt_started, step.attempt_finished | attempt_id, attempt_index, operation_id, outcome и error_code при ошибке |
| agent.message, agent.tool_call | session_id, source_event_id при наличии, текст/артефакт; tool name и status для вызова |
| command.started, command.finished | command_config_id, program_id; exit_code, outcome, output_artifact_ids при завершении |
| artifact.created, context.collected | artifact_id, manifest_id, размер, content_hash; omissions для контекста |
| condition.evaluated, transition.selected | expression_ref/result true/false/null; edge_id и assignments_ref |
| plan.item_changed | plan_item_id, from/to, evidence_ids, commit_shas |
| git.commit_intent_saved, git.commit_created, git.no_changes | intent_id, parent_sha, expected_tree; commit_sha/actual_tree при коммите |
| error.technical, recovery.result | code, retry_safety, operation_id, evidence_refs и принятое решение |
| budget.updated, budget.exceeded | имя, observed/estimated/unknown, использовано, лимит, revision |
| model_group.candidate_selected, model_group.candidate_skipped, model_group.candidate_switched | group_id, group_revision, member_id, member_index, kind=agent\|llm, profile_or_connection_id, model_id, reason; switched дополнительно содержит previous_member_id и history_length |
| model_group.exhausted | group_id, group_revision, kind, history_length и diagnostics_ref со всеми позициями; last_member_id необязателен, поскольку вызовов могло не быть |
| stream.gap | диапазон внешней истории, причина невозможности восстановления |

`stream.reset_required` и SSE-heartbeat — транспортные сообщения, они не занимают sequence доменного журнала. Event schema и OpenAPI экспортируются как типизированный каталог и проверяются в CI.

## 4. Ошибки и ожидание

API-ошибка: `{code, message, details, request_id, retryable}`. Ошибка шага дополнительно хранит `operation_id`, `retry_safety=safe|unsafe|unknown`, `external_outcome` и ссылки на диагностику. Значение retryable не разрешает повтор без проверки retry_safety.

| Код | Что разрешает продолжение |
| --- | --- |
| missing_data | Допустимые evidence собраны и заново проверены |
| permission_required | Ответ на конкретный ожидающий запрос harness в пределах snapshot policy |
| limit_exceeded | Политика лимита изменена с аудитом или Run отменён |
| auth_required, secret_unavailable | Авторизация/SecretStore восстановлены, выполнена диагностика |
| model_unavailable | Выбранная модель снова доступна; смена модели требует нового Run |
| model_group_exhausted | Доступ восстановлен; явное продолжение разрешает новый ограниченный проход прежнего snapshot, сохраняя историю и счётчики. Выбор вне snapshot требует нового Run |
| external_change_detected | Изменения сверены и evidence обновлены; чужие изменения не присвоены запуску |
| unknown_external_result | Recovery подтвердил результат либо отсутствие эффекта; новый платный запрос требует явного решения при неизвестной обработке |
| invalid_response_format | Получен допустимый результат в рамках лимита исправления формата |
| workspace_conflict | Подтверждено отсутствие живого владельца и исправлена резервация |
| process_not_responding, port_unavailable | Дерево процессов/транспорт приведены в подтверждённое состояние |
| path_violation, import_trust_required | Исправлена конфигурация/доверие до старта; расширение действующих разрешений требует нового Run |
| schema_unsupported, configuration_invalid | Создана поддержанная версия графа либо установлен совместимый движок |
| storage_unavailable, signing_required | Восстановлено хранилище либо неинтерактивная подпись, исход действия сверен |
| no_progress | Установлена причина повторного выбора той же работы и принято явное решение о продолжении |

В preflight те же коды возвращаются как blockers без создания Run. Восстановление не переводит waiting_input в running только потому, что нажата кнопка.

## 5. Владение процессами

ProcessSupervisor worker реализует `start`, `request_interrupt`, `stop`, `is_running`, `cleanup_stale`. Внешние серверы общие только для ролей одного Run: по одному экземпляру каждого используемого harness на Run и его зарезервированную рабочую область. Разные Run не делят процесс или сессию. Неиспользуемый harness не запускается.

| Ресурс | Создание / контроль / завершение |
| --- | --- |
| API | Фоновый launcher; не владеет агентами и не завершает их при потере браузера |
| Worker | Фоновый launcher; единственный владелец очереди, supervisor и leases |
| Codex app-server | Worker; stdio; отдельные session/thread для ролей внутри одного процесса Run |
| OpenCode server | Worker; выделенный loopback-порт, секрет локального server и фиксированная directory; отдельные session ролей |
| Command/Git и их потомки | Worker supervisor; процессы отдельной попытки внутри контейнера процессов Run |
| Сессия harness | Адаптер; внешний ID и каталог постоянного хранилища сохраняются отдельно от PID |

Реестр процесса хранит process_id, PID, время создания ОС, fingerprint исполняемого файла, Run, workspace identity, worker generation, transport/port, credential reference и health. PID без времени создания не является доказательством владения. AgentSession хранит harness/version, external_session_id, роль, cwd identity, process_id, последнее внешнее событие и число продолжений.

На Windows supervisor создаёт закрытый Job Object для процессов Run с kill-on-job-close, помещает процесс в Job до продолжения его запуска, запрещает breakaway и не передаёт потомкам handle владения Job. Используется CREATE_NO_WINDOW. Цель — остановить также потомков Node/Python/Git при смерти worker. Возможности Job Objects и их ограничения проверяются на целевой ОС; невозможность включить процесс в Job блокирует автономные записи. [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Codex stdio не переподключается к осиротевшему процессу: после разрыва supervisor останавливает принадлежащую Run группу, затем новый процесс открывает сохранённую сессию, только если это подтвердил capability probe. Для OpenCode тоже не выполняется слепой attach к найденному порту: проверяются реестр, секрет, версия, directory и session. В v1 после смерти worker старые управляемые процессы должны завершиться; сессии могут сохраниться.

Порт OpenCode: loopback, динамический свободный порт, закреплённый в реестре после готовности. Если выбранный порт успели занять, максимум 3 новых попытки запуска с новыми портами после подтверждённого завершения прежнего процесса; затем port_unavailable. Проверка наличия свободного порта не считается резервированием. Чужие процессы на занятых портах не завершаются.

Startup timeout — 30 секунд. HTTP health проверяется раз в 5 секунд; у stdio используются состояние процесса/транспорта и поддержанный безопасный probe. Отдельно хранятся worker heartbeat, attempt heartbeat, last_external_event_at и last_health_ok. Отсутствие текста агента не означает зависание; действует общий timeout попытки, а health и отсутствие событий показываются раздельно.

Без активного turn сервер может простаивать до 60 секунд, затем завершаться с сохранением session ID. Waiting permission не считается простоем. Если восстановление сессии недоступно, процесс можно завершить, а следующий вызов будет новой сессией с контекстом; это явно отражается в истории.

Stop сначала использует native interrupt, затем supervisor прекращает всё принадлежащее этому Run дерево по срокам из STATE_MACHINES. Очистка stale-процессов проверяет владельца и отсутствие живой lease; неизвестный чужой процесс не убивается. После смерти worker восстановление учитывает как возможные правки уже остановленного агента, так и неизвестный результат HTTP.

## 6. Capability и деградация

Минимум для регистрации адаптера: выбрать точную модель, запустить задачу, получить итог/ошибку, различить транспортную ошибку и полезный ответ. Для автономного изменения проекта дополнительно необходимы подтверждённые ограничения доступа и работающий supervisor. Каталог capability содержит supported/unsupported/unverified, проверенную версию, дату и fixture/test reference; результаты реальных проверок этапа 0 опубликованы в [матрице интеграций](../integrations/CAPABILITIES.md).

| Возможность отсутствует | Поведение |
| --- | --- |
| list_models | Ручной точный ID, пометка unverified, тест доступа; в полной v1 автоматический каталог обоих harness остаётся критерием готовности |
| stream_events / history | Итог и process status доступны, UI сообщает ограничение; разрыв истории не заполняется предположениями |
| native interrupt | Остановка через supervisor; неизвестный результат отдельно сверяется |
| resume_session | Новая попытка в новой сессии с сохранённым контекстом, без обещания продолжить память старого процесса |
| structured_output | Промпт со схемой, серверная валидация, не более одного исправления формата |
| permissions | Автономные роли с записью запрещены; допустим только fake или действительно изолированный/read-only профиль |
| profile_scope (разные `model_id` или параметры в одном harness-профиле) | В пределах одного профиля кандидаты считаются допустимыми, если он поддерживает заявленные параметры; иначе кандидат помечается `incompatible_profile` |

Fake — явный режим demo/test, не обращается к реальным провайдерам и по умолчанию не пишет в пользовательский проект. В тестовом каталоге умеет сценарные правки/ошибки и воспроизводимые события. UI маркирует simulated, не выдавая его за реальную интеграцию.

TTL моделей — 15 минут. Смена harness version, подключения или ссылки на credential инвалидирует кэш. При direct-выборе недоступная/исчезнувшая модель не заменяется автоматически. Для группы разрешены только кандидаты сохранённого списка по правилам следующего раздела. Неизвестная capability не считается подтверждённой; отсутствие поддержки обязательной возможности исключает кандидата, а невозможность обеспечить разрешения блокирует автономную запись.

## 7. Бюджеты и retry

Обязательны лимиты времени, посещений и внешних вызовов. По умолчанию максимум 100 внешних вызовов Run, включая повторные попытки и запросы исправления JSON. Это вызовы приложения в harness/LLM, а не скрытые внутренние запросы модели внутри harness; последние учитываются только при наличии соответствующей метрики.

Опционально задаются max_tokens и max_estimated_cost с валютой и источником цены. Метрики имеют качество observed/estimated/unknown; unknown не равен нулю. Проверка перед следующим вызовом учитывает доступную оценку входа и лимит ответа. Текущий вызов может превысить оценку; без ограничения со стороны провайдера это не строгая денежная гарантия. Если пользователю нужен строгий бюджет при неполной телеметрии, preflight блокирует такой профиль как неподдержанный.

Активное время считается сохранёнными интервалами: running, retry_wait, recovering, pause_requested, stop_requested. Queued до получения рабочей области, paused/stopped и ручное waiting_input не расходуют этот бюджет. Timeout живой попытки и срок ожидания permission применяются отдельно: ручное ожидание не разрешает бесконечно держать процесс. По умолчанию permission timeout — 30 минут, затем stop с сохранением причины. После сбоя известная часть берётся из heartbeat; неподтверждённый интервал до доказанной остановки либо recovery учитывается консервативно и помечается estimated. Сбой не возвращает потраченный бюджет; долгий простой с неизвестным исходом может потребовать явного увеличения лимита.

При достижении токенов/стоимости/времени новые вызовы запрещаются; активная операция прерывается, если лимит выявлен во время неё, и Run переходит в waiting_input(limit_exceeded) после сверки. Изменение лимита не сбрасывает использование.

Retry: максимум 2 повтора сверх первой попытки, backoff 1 и 2 секунды с jitter до 25%; Retry-After может увеличить задержку, её предел — оставшийся бюджет Run. 429 и 5xx повторяются только если адаптер подтвердил отклонённый запрос без полезного исполнения либо провайдер поддерживает идемпотентный запрос с тем же ключом. Ошибка соединения до отправки может быть safe; timeout после отправки/обрыв потока — unknown. Для 401/403 требуется авторизация, для неверной модели/параметров — исправление конфигурации. Код HTTP сам по себе не доказывает безопасность повтора.

Каждый фактический retry создаёт новую StepAttempt на том же кандидате в текущем StepExecution. Новый StepExecution, включая repair, начинает просмотр списка с первой позиции; пропуски disabled/incompatible сохраняются событиями без расхода внешнего вызова. Каждый вызов, включая fallback, расходует общий бюджет Run; токены и стоимость относятся к фактической модели. Stop/cancel/pause и лимиты проверяются перед retry и перед следующим кандидатом.

Подтверждённая недоступность модели, профиля, подключения, авторизации или квоты позволяет сразу перейти к следующей позиции, если запрос не отправлялся либо доказан отказ без полезного исполнения. Для временной ошибки сначала исчерпываются ограниченные retry текущего кандидата. HTTP 429/5xx сами по себе не доказывают отсутствие исполнения. Ошибка конфигурации, неверный JSON, отрицательный вердикт и permission request не разрешают fallback. Timeout после отправки, обрыв потока и частичные правки с неизвестным итогом требуют reconciliation/waiting_input. Идемпотентный retry одного провайдера не даёт права на повтор у другого.

За один проход движение только вперёд, без зацикливания. Resume прерванного посещения сохраняет кандидата; после сверки незавершённого вызова и подтверждённой недоступности поиск продолжается ниже его позиции. После model_group_exhausted новый проход возможен только по явной команде и после восстановления доступа, с прежними бюджетами. Limit_exceeded запрещает дальнейшие вызовы независимо от числа оставшихся кандидатов.

Command, агентные правки и Git не повторяются по общей политике HTTP. Для них решение основано на retry_safety конкретной операции и журнале эффекта.
