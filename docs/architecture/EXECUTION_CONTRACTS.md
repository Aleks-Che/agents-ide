# Контракты графа, проверок, плана и Git

Статус: решения для реализации v1. Связи: [описание](../PROJECT_DESCRIPTION.md), [runtime](RUNTIME_CONTRACTS.md), [модель угроз](SECURITY_AND_OPERATIONS.md).

Реализованная конфигурационная часть этапа 3, конкретный JSON-формат и ещё не закрытые проверки исполнителя описаны в [GRAPH_VALIDATION](GRAPH_VALIDATION.md). `ok` конфигурационного preflight не является допуском к внешнему действию.

## 1. Версии и preflight

`schema_version` имеет вид major.minor.patch. Major меняет семантику существующего графа, minor добавляет опциональные возможности, patch уточняет схему без изменения исполнения. В v1 поддерживается один major=1 и только реализованные minor/required_features; неизвестное исполняемое поле не игнорируется. `GET /capabilities` сообщает engine_version, поддержанные schema_version/features, схемы узлов и проверенные адаптеры.

Run сохраняет engine_version, schema_version и snapshot_hash. Обновление не переписывает активный Run или старую PipelineVersion. Миграция шаблона создаёт новую версию с отчётом изменений и сбрасывает подтверждение доверия изменённому исполняемому содержимому. Неподдержанный snapshot можно просматривать, но нельзя продолжать: требуется совместимый движок. Обновление при нетерминальных Run допускается только при подтверждённой совместимости; иначе сначала завершение/отмена или сохранение старого runtime.

Лимиты схемы v1: 1 MiB JSON без бинарных вложений, 200 узлов, 400 связей, 64 KiB одного промпта. Позиции и декоративные данные редактора не входят в execution_hash. Сохранение раскладки не изменяет исполняемую версию. Node ID стабилен, display name свободно меняется; копирование узла создаёт новый ID, дублирование всего графа сохраняет внутренние ссылки. Именованные порты можно добавить позже; сейчас редактор обязан проверять/обновлять ссылки при удалении и копировании.

`POST /api/bindings/{id}/preflight` принимает inputs/overrides и возвращает resolved settings с источником каждого значения, execution_hash, errors/warnings, capabilities, оценку передачи данных и Git-план. Целевой полный preflight проверяет граф, входы, роли, выбор модели/группы и актуальность кэша, секреты, программу каждой команды, пути, лимиты, доверие импорту, разрешения и состояние Git. Не реализованные проверки обозначаются unverified по контракту выше. Probe с реальным платным запросом выполняется отдельным явным действием и учитывается как диагностика.

Preflight сверяет прямые и групповые назначения ролей/узлов: agent-группа допустима только для AgentTask, llm-группа — для LLMRequest. В списке видны все кандидаты с порядком, capability, форматом ответа, контекстом и всеми назначениями данных; для каждого выводится источник переопределения роли/узла и конкретная причина `unavailable`, `disabled`, `incompatible`. Ошибочные параметры (например, неподдерживаемое значение reasoning_effort) блокируют запуск, а недоступный первый кандидат не блокирует его при наличии следующего подходящего. Preflight не отправляет платные запросы автоматически.

Типизированный выбор задаётся в `settings.model_selections[role]`, binding, overrides запуска или `node.config.model_selection`. Выбор узла целиком заменяет выбор роли; внутри роли действует запуск → binding → версия → defaults. `role_parameters[role]` разрешаются по тем же уровням. Итоговые параметры каждого кандидата: профиль/подключение → кандидат → роль → `node.config.params`; значения списков заменяются. Идентификатор модели, endpoint, разрешения, инструменты и секреты не являются параметрами генерации. Формат данных и перенос групп реализованы в [MODEL_GROUPS](MODEL_GROUPS.md); проверка возможностей конкретных адаптеров остаётся частью preflight.

Preflight не резервирует каталог и не гарантирует неизменность среды. Start повторно валидирует snapshot и возвращает существующий Run по idempotency_key. Перед первым внешним действием worker снова проверяет изменяемые условия под резервацией. Занятый корректной резервацией каталог означает queued; ошибочная конфигурация не маскируется ожиданием свободного worker.

## 2. Условия и контекст

AST содержит только `const`, `ref`, `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `exists`, `all`, `any`, `not`. Значения типизированы: boolean, number, string, null; не допускаются неявные преобразования, доступ к секретам, filesystem и вызовы функций. Длина строк сравнения ограничена общей схемой.

```json
{
  "op": "eq",
  "left": {"ref": "steps.verify.latest.decision"},
  "right": {"const": true}
}
```

Отсутствующее runtime-значение или null в сравнении даёт unknown. `exists` возвращает false для отсутствующего поля, true для присутствующего, включая null. Ссылка на несуществующий узел/поле схемы или несовместимые типы — configuration_invalid, а не false. `not unknown = unknown`; `all` возвращает false при любом false, иначе unknown при любом unknown, иначе true; `any` возвращает true при любом true, иначе unknown при любом unknown, иначе false. Пустые all/any запрещены схемой.

`steps.<node_id>.latest` означает последний подтверждённый результат нужной области и текущего цикла, не произвольной прошлой итерации. Поля: `raw_result_ref`, `validated_result`, `decision`, `evidence_manifest_id`, `plan_item_ids`, `execution_id`, `attempt_id`, `cycle_id`. Старые попытки доступны как история, но не выбираются условием неявно. `decision=true/false/null` формирует сервер по валидному verdict; техническая ошибка не даёт decision.

Входы task/plan, критерии, модели и разрешения immutable. Новые сообщения — заметки чата; автоматического добавления в промпты v1 нет. Для запроса недостающих данных используется разрешённый resolution-artifact; изменение самой задачи создаёт новый Run. Контекст и шаблоны не могут читать SecretStore.

## 3. Command: выбран список команд

Один Command исполняет непустой список `commands` последовательно; список может быть типизированной ссылкой на `input.verification_commands` из PipelineBinding. Узел сохраняет результат каждой команды. Специальный цикл Python для пресета не нужен.

```json
{
  "type": "Command",
  "id": "checks",
  "config": {
    "commands": [{
      "id": "tests",
      "program": "python",
      "args": ["-m", "pytest", "-q"],
      "cwd": ".",
      "env": {},
      "required": true,
      "success_exit_codes": [0],
      "timeout_seconds": 300,
      "max_output_bytes": 10485760,
      "retry_safety": "safe"
    }],
    "failure_policy": "collect_all",
    "result_output": "checks"
  }
}
```

`program` разрешается preflight в точный исполняемый путь; `args` передаётся массивом без shell-конкатенации. Явный shell возможен только как видимая, отдельно разрешённая программа/скрипт. `cwd` — относительный путь внутри разрешённой рабочей области. Окружение строится из минимального списка ОС и явного `env`; ключи LLM/локального API/harness не наследуются Command. Секретные значения запрещены в program/args/env/URL, shell-подстановок нет.

`required=true` означает, что для положительной проверки нужен completed с кодом из success_exit_codes; не обязательно только 0, но в пресете default=[0]. `failure_policy=collect_all` продолжает после ожидаемого неуспеха теста, `stop_on_failure` оставляет последующие команды skipped. Required skipped/timeout/failed препятствует passed. Невозможность запустить программу или потеря процесса — техническая ошибка узла, а не факт найденного дефекта кода.

При stop не стартует следующая команда. Повтор после остановки не повторяет уже выполненные unsafe/unknown команды: сверяется subcommand ledger. Для набора безопасных проверок можно повторить весь набор; каждая новая попытка сохраняется. Максимум 50 команд в узле, общий timeout узла также действует. Вывод до лимита сохраняется артефактом; дальше поток дренируется без накопления, ставится truncated=true и счётчик пропущенных байтов. Обязательное доказательство, зависящее от обрезанной части, считается неполным.

## 4. CollectContext и доказательства

`sources` — типизированный список file/glob, diff, artifact_id и command_report_id. `context_paths` подставляется только в file/glob; оно не является списком произвольных действий. Все пути относительны workspace, проверяются до открытия с учётом junction/symlink, [правила путей](SECURITY_AND_OPERATIONS.md) обязательны и для запросов verifier.

Пределы по умолчанию: 100 файлов, 256 KiB на файл, 2 MiB пакета, 64 KiB краткого резюме; задаются в snapshot и дополнительно ограничены моделью. Текстовые пути, exclude patterns, включение untracked и стратегия обрезки видны в настройках. Binary, недоступные, секретные и слишком большие файлы отмечаются в omissions с причиной. Отчёт исполнителя — отдельный источник, не замена коду и результатам тестов.

ArtifactManifest включает artifact_id, schema/media type, byte length, content_hash, источник, Run/execution/attempt/cycle, плановые ID, список файлов с хэшами, base/current HEAD, redaction/truncation/omissions и время. Артефакт сначала записывается во временный файл и атомарно публикуется, затем manifest регистрируется в БД; незарегистрированные остатки убирает GC. Файл, который изменился во время чтения, перечитывается ограниченно либо отмечается нестабильным.

Evidence считается актуальным только для проверенного manifest. После любой правки повторяются необходимые проверки. Общая финальная оценка включает diff от baseline, историю коммитов и код, а не только пустой working diff после последнего коммита. Прогресс хранит ссылки на неизменяемые доказательства; сам boolean passed без них не переводит пункт в done.

### Ограниченное дополнение evidence

Verifier возвращает `missing_evidence` как массив объектов `{kind, path|artifact_id|command_id, reason}`. Разрешены только типы file, artifact, command_report. Никакие команды, пути вне разрешённых sources или новые разрешения из этого ответа не исполняются.

В пресете выход unknown проходит через обычные узлы: CollectContext в режиме `resolve_requests` → Command с отфильтрованными ID из исходного verification_commands (если нужны отсутствующие отчёты) → CollectContext в режиме `collect` → та же проверка. `resolve_requests` только валидирует заявки и формирует allowed_requests/command_ids/denied_requests; он не запускает процессы. Эти режимы и возможность фильтрации Command по ID входят в общую схему узлов.

Повторно запускать по такой заявке можно только заранее настроенные команды с retry_safety=safe; исходный argv менять нельзя. Пустой список выбранных команд даёт skipped узла без внешнего вызова; это исключение разрешено лишь для фильтра, не для неполной конфигурации Command. Ранее обязательные проверки не исчезают из агрегированного результата, даже если их не выбрали для дополнительного запуска.

Максимум 2 возврата по сбору evidence на одну проверку одной части плана. Запрещённая заявка, отсутствие нового evidence или исчерпание лимита ведут в waiting_input(missing_data). После ответа пользователя повторяется проверка, пользователь не может кнопкой назначить passed. Все запросы/отказы/собранные данные видны в событиях.

## 5. Структурированный план и политика сессий

Исходный свободный текст сохраняется полностью. Пользователь может до запуска разбить его на пункты; без явной разбивки весь текст становится одним пунктом P1. Автоматическая разбивка моделью — предложение, которое нельзя подменить вместо подтверждённого плана. MVP не требует отдельного LLM-запроса для разбиения.

PlanItem: `id`, `order`, `title`, `acceptance_criteria`, `status=pending|in_progress|done|failed`, `evidence_ids`, `commit_shas`, `related_execution_ids`. Критерии и ID входят в snapshot; статусы и связи — изменяемая серверная проекция. План хранится внутри Run как версионированный JSON с индексируемыми ID; отдельная таблица допускается только при необходимости запросов.

Добавляется общий тип узла **PlanControl** с операциями `select_next`, `record_verified`, `record_final_check`, `attach_commit`. Его схема объявляет ссылки на проверку/коммит и ID плана. Этот узел переиспользуем в других графах; движок не содержит ветки «если это встроенный пресет».

`select_next` выбирает первый pending/failed по зафиксированному order. Он записывает `work.current_plan_item_id`, `work.scope`, `work.plan_item_ids`, `work.completed_items`, `work.remaining_items` и режим. Агент реализует выбранный пункт и не заменяет критерии. Для repair сохраняется тот же ID, для next_item выполняется новый select_next.

Проверочный JSON расширяется `item_results`: массив `{plan_item_id, verdict, evidence_ids, findings}`. Поле remaining_items содержит ID, а не новые формулировки задачи. Неизвестные ID, пропущенные при обязательной полной проверке пункты и попытка произвольно выбрать уже done пункт отклоняются. Финальный failed может переоткрыть done только через record_final_check с конкретным дефектом и актуальными evidence.

В пресете record_verified переводит текущий пункт в done после успешной проверки после ревью и подтверждённого GitCommit/no_changes; attach_commit сохраняет SHA, если он создан. record_final_check сверяет каждый пункт и возвращает дефектные в failed. Run завершается только при passed для всех исходных пунктов и отсутствии required checks failures. Если план без Git, версия pipeline должна явно иметь другую политику завершения пункта.

Два последовательных внешних цикла без изменения code manifest, статусов пунктов и набора замечаний дают waiting_input(no_progress), даже если общий лимит ещё не достигнут. Изменение timestamp или перефразирование резюме не считается прогрессом.

Реализация может продолжать сессию в режиме repair не более 3 раз; после этого новая сессия с кратким резюме, текущими дефектами и evidence. Для нового пункта по умолчанию новая сессия. Проверяющие используют отдельные сессии от реализации. В API обычной LLM включается содержимое выбранного evidence, а не недоступные ей локальные ссылки. Полная история сохраняется для пользователя, но не отправляется каждый раз. Суммаризация не заменяет первичные доказательства.

Выбор исполнителя: AgentTask выбирает direct-профиль или agent-группу; LLMRequest — direct-подключение или llm-группу. Кандидаты группы просматриваются по snapshot Run. Прямой выбор модели замене не подлежит. При смене профиля/harness агент получает новую AgentSession с актуальной задачей и ограниченным контекстом; native session ID не переносится между кандидатами, сначала сверяется отсутствие живой предыдущей операции. Для LLM каждый кандидат группы получает тот же логический запрос и пакет evidence со своими ключом и параметрами; credentials разных подключений не смешиваются. Resume прерванного посещения сохраняет своего кандидата, пока он доступен; после подтверждённой недоступности поиск продолжается ниже его позиции.

## 6. Git: ветка, baseline и грязное дерево

`branch_policy=run_branch|current`. Default — новая `agents-ide/run/<run_id>` от исходного HEAD в том же рабочем каталоге. Пользователь до старта видит, что рабочая ветка переключится и останется выбранной после Run. Режим current требует явного выбора, сохраняемого в binding; повторного подтверждения каждого коммита не требуется. Detached HEAD допускает run_branch от фиксированного SHA, но не current. Автоматического stash, reset, checkout назад, merge или push нет.

Baseline включает HEAD, ветку, `status --porcelain=v2 -z`, список staged/modified/untracked, метаданные и хэши защищаемых файлов, manifest и локальную ссылку `refs/agents-ide/run/<run_id>/baseline` на исходный commit. Эта ref сохраняет только commit, не незакоммиченные файлы, и не является их резервной копией. Восстановление файлов выполняется отдельно пользователем.

`dirty_policy=strict|allow_nonoverlap`:

- В обоих режимах индекс в начале должен быть чистым; существующее staged не включается в Run.
- Strict блокирует существующие tracked-изменения и untracked внутри разрешённой области записи. Ignored файлы и untracked вне этой области не требуют очистки, сохраняются как защищённые и не коммитятся.
- Allow_nonoverlap включается явно до старта и разрешает изменения пользователя только вне области записи/проверки запуска. Их baseline сохраняется, содержимое не передаётся агенту без необходимости и не включается в коммит. Режим доступен только если адаптер обеспечивает нужные ограничения доступа; иначе preflight предлагает strict.
- Пересечение с пользовательскими изменениями в том же файле блокирует запуск/коммит. Автоматически отделять hunks автора и агента v1 не пытается.

Перед началом каждого рабочего шага и после него сравниваются manifests и ожидаемая ветка. На паузе внешние изменения не запрещены ОС, поэтому при resume они обнаруживаются. Baseline и файловые хэши не доказывают авторство: любое непредвиденное изменение проверяемого файла делает прежние evidence недействительными. Внешняя одновременная запись в тот же файл требует остановки/сверки; система не обещает физическую изоляцию текущего checkout.

GitCommit формирует кандидат только из allowlist проверенных файлов с учётом удаления/переименования. Используется отдельный временный index, не пользовательский index; перед запуском его дерево сравнивается с проверенным manifest. Глобальные настройки Git не меняются. Если кандидат равен HEAD, сохраняется no_changes, а проверка всего плана всё равно выполняется.

## 7. Коммит, hooks и неизвестный результат

Уточнение реализации: staging кандидата использует только временный index. После
проверенного коммита ранее чистый пользовательский index согласуется с новым HEAD
под `index.lock`, если его hash не изменился. Чужие staged-правки не перезаписываются.
Пределы и восстановление описаны в [GIT_PLAN_RUNTIME](GIT_PLAN_RUNTIME.md).

До вызова Git сохраняется intent: operation_id, Run/execution/attempt, branch, parent_sha, expected_tree, allowlist, message_hash, baseline_ref и разрешённая политика hooks/signing. В сообщение включается служебный trailer с intent ID для сверки. После вызова сохраняются SHA, actual_tree, stdout/stderr и состояние рабочих файлов.

Hooks и signing считаются исполняемым кодом/внешними процессами. Preflight показывает их наличие; разрешённая политика и fingerprint hooks фиксируются до старта. Настроенные hooks не выключаются незаметно. Интерактивная подпись, отказ hook или зависание получают timeout/signing_required, без ожидания в невидимом окне. Изменение hooks/config во время Run блокирует дальнейший коммит до сверки.

Если hook изменил дерево до коммита и Git завершился отказом, нужна повторная проверка изменённых файлов. Если коммит уже создан с деревом, отличающимся от expected_tree, запись об этом сохраняется, Run переходит в waiting_input(external_change_detected); коммит не объявляется проверенным, автоматический reset/amend не выполняется. Повторные проверки и последующий исправляющий коммит допустимы после разрешения ситуации.

При crash после Git до БД recovery ищет commit по branch/parent/tree/trailer и сверяет текущую ветку. Однозначное совпадение регистрируется без повторного git commit; отсутствие доказанного исхода — unknown_external_result. Наличие commit с другим tree/parent не принимается только из-за совпавшего сообщения. Пока исход не установлен, блокировка рабочей области сохраняется.

Тесты обязательны для no_changes с незавершённым планом, dirty baseline, внешних изменений на паузе, переименований/удалений, hook с правками, интерактивной подписи, crash после commit и неожиданного движения ветки. Полноценные worktree остаются за пределами v1.

## Council: подтверждённый вход плана (ревью 16.09.2026)

Текущая частичная реализация 9A описана в [PLANNING_COUNCIL](PLANNING_COUNCIL.md). LLM-участники получают одинаковые зафиксированные задачу и текстовый контекст; merger получает полное содержимое минимум двух валидных черновиков. Обязательный JSON содержит текст, шаги/критерии и явный список вопросов. Ответы/правки создают новую ревизию. Подтверждение последней готовой ревизии связывает полное содержимое и ответы hash, повтор идемпотентен. Подтверждение не запускает код. PlanningSource в preflight/RunStart фиксирует тот же план и P1..Pn в snapshot; другой проект, неподтверждённая ревизия и переопределение входов запрещены. Windows harness работают через общие адаптеры и supervisor; выбранные файлы передаются фиксированным read snapshot. Нативный merger получает доступные файлы артефактов, HTTP — полный ограниченный пакет содержимого. Реальные условия приёмки перечислены в PLANNING_COUNCIL.
