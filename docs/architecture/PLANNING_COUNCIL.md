# Council: подготовка и подтверждение плана

Статус 17.09.2026: реализован серверный цикл Council для LLM и нативных Codex/OpenCode. Доступны agent/llm direct/group, merge, ответы/правки, подтверждение, retry и явный одиночный план. Нативное выполнение разрешено на Windows: Codex 0.153.4 использует именованный профиль чтения изолированного каталога, OpenCode — `--pure` и запрет всех инструментов. Реальный смешанный Council получил два черновика (Codex gpt-5.6-sol и OpenCode MiniMax-M3); объединение проверено локальным HTTP-исполнителем. Полностью нативный merger и полная матрица реальных сбоев остаются отдельными проверками.

## Исполняемый контракт

Council хранится отдельно от Run в planning_jobs, planning_members, planning_attempts, planning_drafts, planning_revisions, planning_answers, planning_events. Миграция `0019_planning_native` добавляет журнал процессов попытки; `0018_native_catalog` — метаданные и fingerprint каталога. Миграция `0014_council_safety` дополняет исходную `0013_planning_council`; `0015_council_retry` добавляет отдельные версии доступа для явного восстановления ключей. `0016_council_single_member` разрешает автора single_member; перестройка ревизий атомарно сохраняет связанные ответы, индексы и триггеры при включённых FK. Downgrade при наличии single_member запрещён до любых изменений: авторство не подменяется. Создание использует idempotency key и хеш всего запроса; повтор с иным содержимым даёт 409. Проект и чат проверяются на принадлежность и доступность.

Пользователь выбирает 2–3 участников и отдельный слот merger; UI предлагает 3 участников. Каждый слот допускает direct/group типа agent или llm. Для LLM фиксируются подключение, версия, порядок кандидатов, параметры и ссылка на секрет; для agent — профиль, версия, executable, настройки и fingerprint нативной авторизации/конфигурации. Значения секретов не сохраняются в snapshot и не возвращаются браузеру. Изменение закреплённого ресурса исключает кандидата до явного восстановления доступа. Группа является цепочкой fallback одного слота. Исторические задания с четырьмя участниками остаются читаемыми; новые ограничены тремя.

Участники вызываются последовательно и получают одинаковую задачу и фиксированный контекст. `context_paths` выбирает до 32 файлов, максимум 64 КиБ на файл и 256 КиБ суммарно. Получение пакета держит BEGIN IMMEDIATE, исключает активные пересекающиеся резервации и блокирует запуск новых writers приложения. На Windows directory/file handles удерживаются до окончания копирования без разрешения замены/записи; проверяются конечный путь, ссылки, размер и повторный hash. `.env`, credentials, `.git`, обход пути, symlink/junction и hard links запрещены. После копирования live workspace не используется: изменения проекта не меняют пакет участников. Без файлов остаётся режим provided_text. Все исходные файлы, хэши и scope сохраняются в snapshot; симуляция по-прежнему не получает workspace.

Независимость определяется либо нормализованным endpoint + model ID (для LLM), либо model ID среди всех agent-кандидатов независимо от harness kind. Ключ подключения и смена harness не создают отдельного голоса. Известные прямые дубликаты отклоняются; в группе уже использованная фактическая модель пропускается. Независимость неизвестных alias этим не доказывается. Merger может повторять модель участника, поскольку не считается отдельным голосом.

Merger получает полные тексты валидных черновиков, задачу и общий контекст. Требуются минимум два независимых принятых черновика. Два из трёх дают уменьшенный состав; единственный сохраняется для диагностики, но не становится готовым Council до явного `promote_single`.

## Формат и подтверждение

Исполнители возвращают JSON PlanDocument: непустой body_text, 1–100 steps с непустыми acceptance_criteria и обязательный questions. Вопросы имеют уникальные ID, тип single/multi/text, допустимые варианты и явный allow_text. Только явный questions: [] означает отсутствие вопросов. Отсутствующее поле, Markdown (none), невалидный/усечённый ответ не означают готовность.

Предел документа — 64 KiB UTF-8; диагностическое тело каждой попытки ограничено тем же размером. Допускается одно исправление формата на слот за общий бюджет. Невалидный ответ или ошибка конфигурации не переключают группу. Forward-only fallback применяется к подтверждённой безопасной недоступности и отказу авторизации; неизвестный исход запрещает дальнейшие обращения.

Ответы принимаются только для последней ревизии и всех её вопросов одновременно. Они создают новую ревизию; старые не меняются. Ответы добавляются в показываемый текст и сохраняются структурированно. Ручная правка задаёт полный JSON-документ, включая шаги/критерии/вопросы. Автоматического повторного merge после ответов сейчас нет. Максимум 16 ревизий на подготовку.

confirmation_hash охватывает ID задания, номер ревизии, весь текст, документ со шагами/критериями, вопросы и ответы. Подтверждение проверяет последнюю готовую ревизию, hash и целостность документа. Повтор того же подтверждения идемпотентен; устаревшая ревизия или иной hash дают 409. Триггеры БД запрещают обновление/удаление подтверждённой ревизии. Подтверждение не запускает код.

PlanningSource передаётся одинаково в preflight и RunStart. Допускается только подтверждённая ревизия того же проекта. Сервер фиксирует task, plan, plan_items, planning_text, planning_questions, planning_answers, planning_revision_hash, planning_provenance; попытка переопределить их отклоняется. План получает последовательные ID P1..Pn и попадает в execution hash, snapshot и PlanItem. Существующий PlanControl читает эти пункты без отдельного нового исполнителя. Выбор пункта не является доказательством его выполнения.

## Подготовка Council через harness

Прямой `DirectAgentSelection` и agent-группа доступны через REST/UI для нативного Windows executable с допустимой политикой. Gate проверяет весь состав, включая merger, до первого вызова; неподдержанная платформа/обёртка/политика возвращает `council_harness_real_unverified` или `council_harness_unverified`. Непустые параметры сверяются со свежими метаданными модели. Внутренний simulated-флаг отсутствует в HTTP-контракте.

Кандидаты сохраняют `kind='agent'`, `harness_profile_id` и снимок `harness: {id, name, harness_kind, executable_path, settings, version}`. У группы до фактического выбора `selected_harness_*` пусты; после попытки API возвращает закреплённые имя/kind выбранного профиля. Переименование текущего профиля не переписывает историю.

Worker формирует AgentAdapterRequest с общими task/context/manifest, role/model/params/deadline и output schema. Каждая попытка получает новый приватный scratch-каталог и чистую сессию. `request.md` и `context.json` содержат пакет; только merger получает отдельные `draft-N.json` и все принятые тексты. Codex видит объявленные файлы в профиле чтения scratch и SYSTEMROOT, сеть инструментов выключена, approvals=never, MCP-серверы и дополнительные инструменты отключены. OpenCode получает весь текст в запросе и deny-all permissions. Исходный проект процессу не передаётся. Нативные thread/session/turn ID сохраняются до зависимых действий. Общая валидация PlanDocument применяется после любого адаптера.

Симуляция поддерживает стандартные `responses` с node/attempt/visit, задержками и исходами. Совместимые `harness_body_text[:node_id]`, `harness_outcome[:node_id]` и `harness_error_code` нормализуются в тот же сценарий; для LLM ключи `harness_*` отфильтрованы. Значение пустой строки сохраняется как невалидный ответ, а не заменяется успешным планом. Стандартный план строится JSON-сериализацией, а не конкатенацией строк.

Настройки проверяются теми же validate_settings, что runtime: OpenCode требует no_tools, включённый auth и отсутствие собственных env/serve_args; Codex требует read_only, approval_policy=never (по умолчанию) и отсутствие собственных env/serve_args. Нарушение даёт `council_harness_unverified`. Это проверка декларации конфигурации, а не результат проверки фактических прав процесса.

При retry с refresh_credentials повторно проверяется политика. Смена kind/executable/settings требует нового Council (`planning_retry_harness_changed`). Обновление каталога или авторизации при неизменной конфигурации фиксируется отдельной версией доступа и fingerprint; исходный snapshot не переписывается. Повторные проверки перед запуском не позволяют незаметно использовать изменившуюся авторизацию. Архивный профиль недоступен.

## Worker, бюджет и восстановление

Захват задания — BEGIN IMMEDIATE, lease 30 секунд, owner + generation. Heartbeat обновляет lease; последующие записи сверяют владение. Намерение planning_attempts и резерв вызова фиксируются до внешнего обращения. PlanningSupervisor использует общий ProcessSupervisor/Windows Job Object; PID/create_time/owner/generation записываются до возобновления suspended процесса. Retry дополнительно требует подтверждённой остановки дерева старой попытки. Нормализованные события и очищенные native envelopes сохраняются с лимитом 4 МиБ/2000 событий на попытку и явным признаком усечения; проверяется общая квота хранения. Сетевой запрос выполняется вне SQLite write-транзакции. Завершение и черновик сохраняются отдельной короткой транзакцией.

Общий лимит 1–64 вызова (по умолчанию 8) включает fallback, исправление формата и merge; время 10–3600 секунд (по умолчанию 600). Лимит конкурентности является верхней границей, фактическая конкурентность внутри задания равна 1. Token/cost показываются только при наличии данных; external_calls учитывает зарезервированные попытки, включая отказ до отправки. Перед каждым обращением проверяются бюджет, отмена, lease и доступность закреплённого ресурса.

Отмена переводит задание в cancelled, прерывает локальное HTTP-ожидание и запрещает следующий вызов. Это не гарантирует прекращение вычисления у удалённого провайдера. При restart завершённые черновики и бюджет сохраняются. Если осталась running-попытка, она получает unknown, задание — failed с unknown_external_result; запрос автоматически не повторяется. Старые задания 0013 без достоверного request hash/намерений получают legacy_planning_unverifiable, без платного replay. Старые ревизии без полного документа нельзя подтвердить или перенести в Run.

Состояния: drafting → merging → needs_answers | ready_for_confirmation → confirmed. Ответы/правки создают новую ревизию в needs_answers или ready_for_confirmation. Cancelled и confirmed терминальны. Failed допускает явный `POST /planning_jobs/{id}/retry` или принятие единственного проверенного черновика через `promote_single` по правилам ниже; автоматического replay нет. Ошибки и последние 200 событий доступны в API/UI; полные попытки и события сохраняются в БД.

### Явное восстановление доступа

Retry сверяет `expected_state_version` под BEGIN IMMEDIATE. Указываются либо все неуспешные слоты (`reset_all_failed=true`), либо список выбранных `reset_member_indices`; неизвестные/дублирующиеся индексы, сочетание двух форм и попытка сбросить succeeded/pending отклоняются. Подмножество failed/skipped разрешено; все unknown/running необходимо разрешить явно, исключать их из выбора нельзя. Уже принятые участники не вызываются повторно; при отказе только merger повторяется только merger.

Живой lease блокирует retry. После истечения/освобождения lease увеличивается generation, прежнее владение снимается, оставшиеся running-попытки фиксируются как unknown. Поздний `_finish` старого worker отвергается. Для слота unknown/running необходимо отдельное `acknowledge_unknown_result=true`: UI показывает явное согласие на возможное повторное выполнение и оплату. Это разрешение новой попытки, а не утверждение, что старый запрос не выполнился. Локальная остановка HTTP не доказывает остановку удалённого вычисления.

Сбрасываются статус выбранных неуспешных слотов и позиция кандидата (новый проход с нулевой позиции). Подмножество failed/skipped разрешено: остальные сохраняются без повторных вызовов, merge требует прежние два принятых черновика. Все unknown/running необходимо включить в явное разрешение с acknowledge_unknown_result; оставлять их неразрешёнными нельзя. Сохраняются история всех попыток и диагностические черновики, принятые результаты, контекст/манифест, ревизии, общий счётчик вызовов и лимит одного исправления формата на слот. `started_at` не меняется: общий wallclock-дедлайн включает время ожидания в failed. Исчерпанные лимиты не продлеваются; для нового бюджета требуется новое задание. Недостоверное legacy-задание и изменённый контекст retry не обходят.

`refresh_credentials=true` разрешает использовать текущую версию доступа только для того же ID подключения с точно тем же base_url. Порядок/состав группы, model ID, параметры и исходный `candidates_json` не меняются. Новые version/secret_reference хранятся отдельно в `access_overrides_json` только для pending/сбрасываемых слотов (включая ещё не запущенный merger); каждая следующая попытка фиксирует фактический доступ в своём ledger. Архивный ресурс остаётся недоступным, смена endpoint требует нового Council. Последующая правка подключения снова требует явного retry. SecretStore читается непосредственно перед HTTP; значения ключей и ссылки на них не попадают в API/события.

Событие `planning.retried` сохраняет фактически сброшенные/сохранённые ID, generation, число уже зарезервированных вызовов, ID слотов с подтверждённым unknown и изменения версий доступа без секретов. Одновременный/повторный запрос со старой state_version даёт 409, не создавая дополнительного прохода. Retry не имеет отдельного idempotency key: после потерянного ответа UI перечитывает задание, а не отправляет новую команду с новой версией автоматически.

### Явный одиночный план при потере кворума

`POST /planning_jobs/{id}/promote_single` принимает задание в `failed` с `last_error.code=council_quorum_missing` и ровно одним принятым участником. Обязателен JSON boolean `confirm_degraded=true`; отсутствующее/ложное значение, строки и числа возвращают 422 `validation_error`. `expected_state_version` сверяется под BEGIN IMMEDIATE: параллельные promote/retry не создают две ветки продолжения.

Живой lease запрещает promote (`planning_worker_active`); после освобождения/истечения владение снимается, generation увеличивается. Незавершённые попытки и pending/running/unknown участники запрещают принятие (`planning_work_unresolved`). Проверяются request hash, hash закреплённого контекста, принадлежность черновика заданию, accepted/parse_status, body_truncated, byte_length и content_hash. Повторный parse_document проверяет полный JSON/критерии/вопросы; повреждение возвращает 409 `planning_single_member_invalid`, без ревизии и события. Legacy или изменённый контекст также не обходятся.

Из принятого черновика создаётся ревизия автора `single_member` через общий add_revision. Состояние переходит в `ready_for_confirmation` или `needs_answers`; текущие last_error/finished_at очищаются, прежнее событие ошибки остаётся в истории. merged_by_member_id указывает на принятого участника, n_participants_actual=1, degraded=true. Невалидные/неуспешные черновики, попытки, исходное started_at и использование бюджета сохраняются. Promote не вызывает модель, поэтому исчерпанный бюджет не запрещает принятие уже проверенного результата.

Ревизия требует обычных ответов/ручных правок и отдельного confirm перед RunStart. Уменьшенный состав сохраняется и у последующих user-ревизий. Сервер фиксирует planning_provenance (degraded, запрошенное/фактическое число участников, автор текущей ревизии и source_member_id) в защищённых inputs и immutable snapshot Run; подмена через inputs запрещена. `/runs/{id}/snapshot` и экран Run используют сохранённый признак. Старые Run без этого блока возвращают null, их происхождение не достраивается из изменяемого текущего задания.

Повторный promote после успеха даёт 409 `planning_state_invalid`; неверное число принятых участников — `planning_single_member_count`; другой last_error.code — `planning_quorum_required`. planning.single_member_promoted записывает номер ревизии, число участников, ID/модель принятого участника, ID/hash черновика и generation, без секретов. UI требует отдельного чекбокса и после любого исхода мутации перечитывает состояние; потерянный HTTP-ответ не вызывает автоматического повторного promote. Автор ревизии и пометка уменьшенного состава видны пользователю.

## Граница этапа и исходники

Остаются реальные проверки полностью нативного объединения, длительного выполнения и восстановления после сбоя на каждом harness, а также полная матрица A71–A74. Запись в проект Council не разрешает. Одиночный план при потере кворума требует `promote_single` и `confirm_degraded`; подтверждение плана остаётся отдельным действием.
