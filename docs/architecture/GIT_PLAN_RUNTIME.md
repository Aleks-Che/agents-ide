# GitCommit и выполнение фиксированного плана

Действующий серверный контракт этапа 8 после ревью от 15.09.2026. Сценарии
исполняются обычным Runner: тестовый AgentAdapter изменяет временный проект,
настоящий HTTP-адаптер обращается к локальному тестовому провайдеру, Command и Git
запускают настоящие процессы. Производственный AgentTask остаётся за gate 6A;
положительный результат этих тестов не подтверждает работу платной модели или harness.

## До первого исполнителя

Preflight проверяет входы, все обязательные роли и существование ресурсов direct/group.
Для Git он только читает репозиторий: проверяет HEAD, чистоту index, dirty policy,
allowlist, hooks и signing. Git executable и fingerprint конфигурации входят в
execution_hash и immutable snapshot. Хеш всей конфигурации сохраняется только для
диагностики и не блокирует запуск или коммит при изменении общих настроек worktree.
Чужие staged-изменения блокируют Start.

Под резервацией Runner повторяет проверку, сохраняет baseline в БД, затем создаёт
`refs/agents-ide/run/<run_id>/baseline` и выбирает ветку. Baseline снимается до
изменений агента, один раз на Run. Создание ref/ветки использует compare-and-swap;
существующая ветка с другим HEAD не сбрасывается. `run_branch` делает обычный checkout,
`current` требует именованную текущую ветку и разрешает коммит именно в неё.

`strict` запрещает исходные tracked-изменения и untracked внутри allowlist.
`allow_nonoverlap` сохраняет хэши исходных изменений вне общей области записи;
пока нет подтверждённого ограничения записи адаптера, preflight запрещает этот режим
для графов с AgentTask/Command. Для серверного графа без этих писателей режим доступен.
Изменения вне общей allowlist, смена HEAD/ветки/hooks/требования подписи и правки файлов во время
паузы останавливают продолжение. Git не делает reset, amend, stash, force checkout или push.

## Коммит и восстановление

GitCommit фиксирует изменения без обязательного узла проверки или формального
`verdict`. Агент перед ним может проверять и исправлять файлы, возвращая обычный
текст. Если графу нужна проверка качества, она задаётся отдельным узлом и условием
перехода. Устаревший `verification_node_id` принимается для совместимости: ссылка
на завершённое выполнение того же Run/scope/цикла сохраняется только как метаданные
для существующих PlanControl-графов. Отсутствующая ссылка, verdict и evidence
предыдущего агента не блокируют GitCommit.

Кандидат собирается из parent во временном `GIT_INDEX_FILE`. Удаления, пробелы в
именах и переименования обрабатываются через NUL-разделённые записи. `*` не пересекает
каталог, `**` поддерживает вложенные каталоги. Ignored и защищённые файлы никогда не
добавляются даже через `**`; `allow_untracked=false` исключает новые файлы.
Git clean/EOL-преобразования работают с текущей конфигурацией и контролируемыми
процессами. Изменение рабочих файлов во время построения дерева блокирует коммит.

До `git commit` сохраняется immutable git_intent: operation/attempt, parent, branch,
expected tree, allowlist, message hash, trailer, baseline ref, manifest и hash index,
необязательный verification ID и политика hooks/signing. Обычный `git commit` сохраняет действие
hooks и настроенной подписи. После вызова проверяются SHA, parent, actual tree,
единственный trailer `Agents-Ide-Intent`, рабочие файлы, hooks и требование подписи.
Неожиданный созданный коммит остаётся в истории с диагностикой и не считается проверенным.

Пользовательский index не участвует в staging кандидата. После подтверждённого
коммита ранее чистый index согласуется с новым HEAD под эксклюзивным `index.lock`,
только если его hash не изменился. Это устраняет ложные обратные staged-изменения
после перемещения HEAD. Чужое staging или lock не перезаписываются; созданный SHA
сохраняется для последующей сверки. Содержимое index не обещается побайтно неизменным.

Recovery сначала доказывает остановку прежнего владельца и дерева процессов.
Точное совпадение branch/parent/tree/trailer регистрирует уже созданный коммит без
повторного вызова. Отсутствие доказанного исхода оставляет `unknown_external_result`;
retry не переисполняет незавершённый intent. `no_changes` также восстанавливается по
parent/tree/manifest и не пропускает оставшийся план или его финальную проверку.

Все Git-вызовы, включая hooks/signing, проходят ProcessSupervisor/Job, ограничение
вывода 16 MiB и deadline (обычно 30 секунд на команду плюс общий deadline узла).
Зависший signer завершается с ожиданием `signing_required`; интерактивное окно не нужно.
Неопределённый отказ hook не разрешает автоматический повтор. Завершённые процессы
удаляются из активного реестра; закрытие Job синхронизировано с heartbeat.

Manifest ограничен 10 000 файлов и 64 MiB суммарного содержимого, включая ignored
файлы для защиты от изменений. Недоступный, перенаправленный или слишком большой
каталог не получает ложного доказательства неизменности. Полноценное управление
worktree, масштабирование manifest и приёмка реального harness остаются отдельной работой.

## План и пресет

Start фиксирует исходный текст и подтверждённые пункты в snapshot и создаёт PlanItem
в одной транзакции. ID назначает сервер (`P1`…); текст без разбивки становится P1.
Название, порядок, критерии, scope и принадлежность Run защищены также триггером
миграции `0011_stage8_review`; статусы и ссылки на доказательства — изменяемая проекция.
PlanControl сохраняет проекцию и результат попытки атомарно, поэтому replay не выбирает
следующий пункт повторно после сбоя.

`record_verified` требует passed и подтверждённый commit/no_changes именно этой проверки
(либо явную политику verified_only). Evidence ID проверяется по реальному артефакту Run.
`record_final_check` требует каждый исходный ID ровно один раз. Passed для pending
не делает его done. Done переоткрывается только новым доказательством конкретного дефекта.
End проверяет все статусы и свежую успешную финальную оценку.

Пресет — обычный JSON-граф с четырьмя ролями без зашитых моделей. Он выполняет
реализацию → команды/контекст/верификацию → ревью → повторные команды и верификацию →
коммит → проверку всего плана → финальные команды и независимую LLM-оценку.
Финальный пакет включает исходный план, разрешённый код, baseline diff и всю историю
коммитов Run. После оставшихся пунктов выбирается следующий ID. Режимы initial,
repair и next_item и лимиты отдельного пункта не сбрасывают бюджеты всего Run.

Evidence-петля начинается до нового сбора контекста. `requests_from_node_id` связывает
resolve_requests с конкретным verifier текущего или непосредственно предыдущего цикла
того же scope. На роль/пункт разрешены два возврата; запускаются только настроенные
safe-команды. Для LLM выбирается последний пакет контекста, свежесть проверяется по
циклу и manifest; старые пакеты не загрязняют новый. Повтор одинаковых циклов ремонта
или финальных оценок без изменения кода/статусов/замечаний даёт no_progress.
Resolve не заменяет проверку вводом boolean passed.

При старте API каталог устанавливает стабильный system template. Обновление графа
добавляет валидированную immutable версию; пользовательские копии не меняются.
`GET /api/presets` даёт каталог, обычные endpoints templates/versions/bindings — настройку,
`GET /api/runs/{id}/plan` — фиксированный план и текущие evidence/commit/status.
Новые семантики объявляются capability `verified_plan_git`.
